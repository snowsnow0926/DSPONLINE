# Rust RP1：终局档恢复来源复核

Role: develop。2026-09-09，未发布。本轮修正先前诊断的入口前提，并补充时间预算回归检查；没有放开 Rust 准入或改动玩家文件。

## 结论与先前结果的区别

此前 `private-runtime-source-buffered-v1` 将原始终局运行态直接交给 Host，确实得到 `offline-macro-time-warp-active`。该结果保留，但它跳过了菜单中已有的恢复步骤，不能据此断言真实“继续游戏”需要新增 timeWarp 兼容实现。

当前 `StartMenu.prepareTimeWarpDeferredLoad()` 先检查恢复日志：匹配的有效主档日志独占该时间段，普通离线时间置零，由游戏恢复流程处理；日志不可用则提示确认；排除匹配日志后，调用 `recoverOrphanedTimeWarpForOffline()`。后者保留已提交游戏状态，将待恢复真实时间计入一次普通离线预算，解除未提交加速事务，然后才调用原生候选入口。

授权终局来源经实际 `inspectSave()` 加载后有 110,042 实体、233,300 条传送带，timeWarp 开启，两项 pending 时间均为 0。本轮没有把原档手动改成合格状态：调用现有生产恢复函数，保留原对象和原文件，验证其他 48 个顶层游戏成员引用不变、重复恢复不再变更状态或时间。没有取得玩家本机日志，因此这些新检查仅覆盖无匹配日志分支。

恢复后的完整工厂经真实 Broker / Host 生成一秒候选，完整 canonical 状态与 JS 参考一致；来源及原档不变，Host 正常退出 0、临时目录清理完成。这是**短时候选正确性**，尚非该终局档的真实菜单完整等待、取消、持久保存或重开验收，也没有新增性能百分比。

## 新增回归与后续
