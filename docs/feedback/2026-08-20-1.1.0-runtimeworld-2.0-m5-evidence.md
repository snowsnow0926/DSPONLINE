## 1. 实现结论

- 将模拟生命周期、主存档持久化生命周期、存档 UI 状态和画布展示发布从 `FactoryGame` 拆成独立边界；底层 envelope、checksum、精确读回、backup、CAS、revision 与 fence 语义保持不变。
- Simulation Worker 在权威状态旁生成 canonical primary/snapshot envelope；Persistence Worker 独立完成 SHA/FNV/checksum 解析、seed/proof 绑定、CAS、IndexedDB 提交、事务内读回和提交后读回，主线程不再为自动保存完整克隆并解码 UI 状态。
- 自动快照只在同一个已验证 primary 身份上准入；旧 primary 备份改为主提交成功后的 best-effort 延迟写入，失败仍保留诊断而不伪造主保存成功。
- `RuntimePrimaryPersistenceLifecycle` 串行化自动保存、手动保存、返回菜单和页面生命周期触发的 primary 意图，修复同页两个上层队列可交叉触发真实 CAS 冲突的问题；没有通过 revision 重写绕过 CAS。
- `RuntimePersistenceViewStore` 与独立通知子组件隔离高频保存状态，避免整页因保存进度重渲染。
- 画布保留稳定的 React Flow 外层节点；纯运行时更新只派生内容确实变化的动态节点。拓扑签名纳入 `interactionLocked`，告警成员不变时复用稳定集合。没有引入未经门禁的全量 canvas 重写。
- 空间站空槽规范化修正为单次即幂等：空槽不再在第二次会话被补出 `itemId: undefined`。这修复了编译缓存暴露出的真实状态形状漂移，而不是在测试里忽略字段。

分块本地存储仍为关闭状态：当前没有满足崩溃恢复、迁移、校验和与回滚门禁的证据，不纳入默认候选。生产路径没有开启 shadow 双跑；旧实现仅保留为受控 fallback、测试 oracle 与诊断入口。

## 3. 正确性与回归证据

- 完整 Vitest：`188 passed / 16 skipped` 文件，`1,503 passed / 29 skipped / 0 failed` 用例。
- 保存阶段专项：手动保存、自动保存、返回菜单按统一生命周期顺序提交，默认保存编辑锁行为保持，`2/2 passed`。
- 真实 A 自动保存开发门禁：`1,050 / 1,384 ms`，最大 Long Task `77 ms`；B：`378 / 536 ms`，最大 Long Task `61 ms`；两档自动快照均通过。
- 既有真实 A 画布密度专项：`4/4 passed`。
- `npm run typecheck` 通过。
- `npm run build:web` 通过；startup gzip 总量 `194,949 B`，JS `101,962 B`，CSS `92,987 B`，最大启动 JS `58,974 B`，禁入启动模块为空。

失败诊断保留了两个领域结论：一是站点槽位形状必须在一次规范化后稳定；二是同页所有 primary 保存意图必须共用上层串行边界。对应修复均落在产品代码并有专项覆盖，没有增加 retry、skip 或比较宽容度。
