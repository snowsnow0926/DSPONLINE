# 网页性能循环开发

Role: develop。以香港 Web 为主，优先产率复制下的真实材料建筑制造和量子配送。开发与测试在独立 D 盘工作树中进行；线上仍为 1.3.1，本记录不授权或代表发布。

第一轮结论：在材料充足的大档建造压力测试中，最重一段计算从约 **2.32 秒降到 1.59 秒**，减少约三分之一。八次最终结果一致；3,528 项单元测试、477 项浏览器测试及生产包离线重开检查通过。这是开发候选，尚未上线，也不代表所有玩家的整体帧率或加载速度提高了同样比例。

## 验收原则

- 原存档只读。所有供料、开关或倍率变化仅发生在明确标记的测试副本。
- 同一初态、推进区间和固定序列化时间必须得到相同的完整结果摘要；同时检查成本、产量和队列。
- 性能包含准备、计算、校验与回写成本；只保留实测改善，单列内存与交互指标。
- Rust/WASM 先验证现有建造和递归模块的可移植接口与端到端成本，再决定是否接入；已有 Windows Host 的局部成绩不当作网页收益。
- 不改变 GameState v47、envelope v2、云格式、自动备份停用设置或产率复制的数值规则。

## 当前循环

1. 固定 1.3.1 源码与原有大档预热副本，复测产率复制的供料压力场景和无供料场景。
2. 对当前仍占用时间的制造/校验路径取 CPU 样本，选择最小可验证改动。
3. 差分与故障测试通过后进行配对复测，记录收益、限制和是否保留。
4. 验证 Rust/WASM 构建及紧凑建造接口，禁止按帧跨边界复制整份大档。

## 第一轮候选：制造任务复用与库存投影

递归计划只携带该目标所有可能配方路线所需的库存项，包括高级路线、未解锁路线和回溯路线；真实全量库存没有被裁剪。一个同步制造阶段复用目标目录和科技资格，目标剩余量与在制任务仍每次读取，因此完成一个目标后会继续正确分配工作。未批处理的独立参考路径保持全库存规划和原始目标查询。

使用 1.3.1 同一预热大档的显式供料压力副本，倍率 8，依次推进到 1 / 10 / 30 墙钟秒。每个独立进程执行两次，顺序为旧、新、新、旧；测量期间不并行构建或运行测试。既有玩家原始存档不参与写入，预热输入文件的前后 SHA-256 相同。

| 指标 | 1.3.1 基线 | 当前候选 |
| --- | ---: | ---: |
| 第一段中位 | 11.12 ms | 9.72 ms |
| 第二段中位 | 1,035.24 ms | 713.95 ms |
| 第三段中位 | 2,317.26 ms | 1,588.88 ms |

第三段耗时减少 **31.43%**。八次完整结果的 SHA-256 均为 `2b56509b5cd28c50e187f1a4c9030bb3fd2b459a9740e57a870c3e51c1613acd`。计时覆盖每次推进调用内的制造、校验和摘要计算，不含预热文件读取、初次传输和最终整档序列化。这只是本机 Node/V8 中的产率复制建造压力用例，不代表整款游戏、香港线上浏览器或所有大档都快了同样比例；RSS 采样不等于峰值内存验收。

证据保存在本机忽略目录 `artifacts/web-performance-loop-20261026/`：`baseline-stress.*`、`projected-inventory-stress.*`、`scheduling-context-stress.*`、四组 `paired-*.json/log` 和 `paired-summary.json`。前两个独立改动分别进行过试测后才组合；性能对照均保留完整结果摘要。

## Rust/WASM 准备

已安装当前工具链的 `wasm32-unknown-unknown` 标准库，并通过现有 `dsp-native-core` 的该目标 `cargo check --locked`。这证明库可以面向浏览器目标编译，不代表已经生成浏览器接口、验证所有计时/线程路径或获得实际收益。下一阶段仍须提取紧凑计算接口、加入浏览器差分测试，并量入量出测量传输和校验成本。

下一轮先准备不接管存档的 Rust 规划计算接口，并与本轮 JS 候选比较；覆盖高级材料到货、缺料、配方回退、多目标和取消。只有计入数据传输、校验、回写后仍更快且结果一致的路径才考虑接入，未验证路径继续使用现有 JS。
