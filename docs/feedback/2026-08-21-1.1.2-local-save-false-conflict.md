# 1.1.2 本地存档“跨标签页覆盖”误报根因与修复证据

## 结论

1.1.1 仍存在一个同页竞态：自动保存已经精确写入并读回主档后，持久化 Worker 会延迟把旧主档滚动到 backup；页面内的 backup catalog/revision 缓存尚未刷新时，随后发生的手动保存或生命周期保存会把这个**同一 writer、同一 fencing token 的新 backup head**误判为另一标签页覆盖。截图中的“已阻止跨标签页覆盖”因此不是存档损坏，也不是第二个标签页写入。

另有一条相邻风险：旧窗口关闭后留下的完整 emergency mirror，在新窗口取得过期租约时原先可能走过早的冲突分支。1.1.2 将它改为先完成租约 CAS，再按完整 lineage 判定是否可安全接续；不满足证明的镜像仍保留为显式冲突。

本报告只覆盖开发修复和隔离验证；没有连接生产、上传玩家存档、修改服务器数据库、排行榜或下载页。

## 竞态时序

1. 保存 Worker 取得权威检查点，验证并提交 primary。
2. 该提交返回后约 50 ms，持久化 Worker 把前一版 primary 写入 rolling backup，并递增 durable backup revision。
3. 页面 UI cache 仍持有旧 backup catalog/revision。
4. 手动或生命周期保存用旧 cache 发起 CAS；旧逻辑只看到 revision 前进，未证明 owner/fence/backup lineage，于是错误抛出跨标签冲突。

真正的跨标签接管会改变 writer 或 fencing token；它与损坏、半写、时间倒退候选仍必须硬冲突并保留两份原文。

## 修复内容

- `src/game/localSaveStore.ts:1078`：对 normal/speedrun main rolling backup 增加严格的 same-fence rolling-head rebase。只有 backup catalog 完整且 valid、slot/mode 匹配、candidate 时间不倒退、durable revision 属于当前 writer/fence、payload/catalog/revision/checksum 全部可验证时才接续。
- `src/game/localSaveStore.ts:902`、`:1532`：租约 claim 返回旧 lease；emergency mirror reconciliation 移到成功原子 claim 之后。
- `src/game/localSaveStore.ts:1284`、`src/game/localSaveCoordination.ts:189`：新窗口只在完整 mirror metadata、payload checksum、mode、primary revision、writer/fence lineage 一致时继续旧窗口镜像；其他情况走公共冲突保留路径。
- 保留 1.1.1 历史版本说明并加入精简的 1.1.2 说明；没有改变 GameState、envelope、cloud schema、SQLite layout 或 IndexedDB 数据格式。
