## 4. raw payload cache P0

### 4.1 复现与根因

旧路径在真实 A 档稳定复现：等待 120 秒后 `getLocalSaveRawCacheSize()` 仍为 1。失败发生在产品 getter，不是 DOM 文案滞后。

根因是 React StrictMode mount 的 effect setup-cleanup-setup 触发同步 `saveGame()`；随后 primary、backup 与 automatic snapshot 通过协调式 IndexedDB 事务提交，但成功读回后没有释放 renderer 内的完整 raw candidate。

### 4.2 修复合同

- 只有 primary、backup、automatic snapshot 在 exact committed value 读回成功后释放 transient raw payload。
- 若同一 key 已排入更新值，不释放较新的值。
- 显式 slot/manual recovery 继续保留，兼容同页同步读取与 tombstone 合同。
- shell 的 raw-cache 属性改为订阅 storage status，避免把真实释放误报为旧 DOM 值。
- 未刷新页面、未清空 IndexedDB、未删除存档。

### 4.3 验证

## 5. 物流 profiler 非重叠归因

### 5.1 计时合同

以下字段是互斥独占阶段，其和与 `logisticsMs` 对账：runtime reset、buffer transfer、material delivery、orbital terminal、lookup maintenance、warper refill、dispatch、route advance、congestion、galactic export。

`peerMatchMs`、`routeEconomicsMs`、`dispatchPeerSortMs` 是嵌套诊断，明确不加入独占阶段之和。profiler 未提供时不调用阶段时钟、不编码 trace，也不改变玩法路径。

### 6.7 画布保留链根因与按节点 selector 修复

最初的 B 档正式趋势不是普通分配锯齿：约 25 分 50 秒时页面存活堆达到 3.67 GiB、renderer working set 达到 4.56 GiB，随后页面 OOM。以下隔离对照逐步缩小了保留链：

| 对照 | 结果 | 结论 |
| --- | --- | --- |
| 暂停 Worker 2 分钟 | 页面堆约 +4.82 MB | 模拟推进是触发条件 |
| 隐藏工厂画布、Worker 继续运行 2 分钟 | 83.54 → 88.81 MB，约 +5.28 MB | 根因在活动画布消费链，不在 Worker 权威状态本身 |
| 只冻结节点推导、Worker 继续运行 2 分钟 | 55,890,496 → 56,156,284 bytes，约 +0.27 MB | 节点发布是决定性保留边界 |
| 正常 32.5 秒计数 | node derivation +158；React Flow 外层发布 +33；每次约替换 40/47 个动态节点 | 每个 runtime revision 都把新的完整节点数组交给 React Flow |

堆分配采样把主要存活分配映射到 `simulationProjection` 和 `FactoryGame` 节点 map/join。产品并没有玩法状态倒退；问题是约 40 个可见动态节点每秒重建并发布整个 React Flow nodes 数组，旧数组又通过 React/React Flow 更新闭包保留大型 `GameState` 投影。

修复保留 React Flow 的交互、位置、选择和无障碍外层节点，只把运行态 `FactoryNodeData` 发布到按 entity id 分片的 render-only `KeyedViewStore`。每个节点用 `useSyncExternalStore` 只订阅自己的 key；静态展示、动态展示切换和同 id 删除/重建都有独立单测，store 不进入 GameState、Worker 消息或持久化。修复后 B 档 30 秒专项中，节点内发布从 3,020 增到 4,319，React Flow 外层发布和 changed total 分别稳定在 6 和 2,281，页面堆只增加约 0.89 MB。

固定运行时代码 SHA 为 `14e2e6abf55863c4dc1a6259d5c29e59ec3bd4c5`，诊断 Build ID 为 `1.0.46+14e2e6abf558`。类型检查、19 项 store/画布单测和以下 Chromium 定向链路通过：运行进度值持续更新、极限 LOD/Canvas 线路、端口拖拽建线、空间站往返后的拖动/框选/拉线。

### 6.9 旧引擎 1h / 24h / 30d 长时债务基线

两份真实档都因仍有建造或递归制造任务而不具备快速近似资格；1h、24h 和 30d 均必须走精确引擎，不能用宏观结果冒充旧引擎 oracle。直接跑完全程会让 M-1 自身阻塞数小时至数天，因此正式基线采用固定 12 个确定性安全边界并双跑：记录精确前缀 hash、pending debt、单边界最大不可让出时间和按同一步长外推的完成时间。它是有界旧引擎基线，不声称 24h/30d 已完成。

## 7. M-1 Go / No-Go

### 7.1 瓶颈与可回收预算排序

1. 模拟领域仍占完整周期约 A 87.3%、B 84.2%；线路在两档都约三分之一，是最稳定的 M2 首迁对象。A 的生产约 32%，B 的物流约 30%，因此 M3/M4 缺一不可。
2. 每个非拓扑命令当前仍完整 rebuild lookup，热样本中占命令预处理约 92%～97%；M1 的局部 domain invalidation 是低玩法风险、高交互收益的首要结构改造。
3. Projection 传输已减少约 99.3%～99.6%，单独重写消息格式只有约 6%～13% 的合理完整周期收益上限；它是 journal 基础，不是 40% 总收益来源。
4. 画布曾存在独立 OOM 保留链，现已用按节点 selector 收口并通过两档 30 分钟门禁；它不再掩盖 Worker 领域基线。
5. 当前保存 UI 全程仍约 A 5.59 秒、B 2.49 秒，主要峰值在序列化/IDB 写入；raw-cache 已归零，但 1.1.0 的 A 2.75 秒、B 1.05 秒目标尚未实现，应留到 journal/checkpoint 数据可证明后处理。

M1 只承诺建立 slot/journal、局部失效和 resumable session，合理整周期收益约 6%～13%；M2 线路领域至少下降 35% 才可能贡献约 11% 完整周期；M3 需把累计完整周期下降推进到至少 35%；M4 才承担两档最低 40%、目标 55% 的最终门槛。各局部百分比重叠，禁止相加宣传。

### 7.2 内存余量与实施限制

- 基准机物理内存约 31.82 GiB。30 分钟后 A/B 页面强制 GC 存活堆约 86.24/68.65 MB，simulation Worker 约 147.77/57.44 MB，renderer working set 约 839.09/704.60 MB。
- 载入/保存 renderer 峰值约 A 1.29/1.47 GB、B 0.92/1.10 GB；开发态短时 shadow 双跑有余量，但生产只能保留一个权威 world，不能把双运行时峰值带入默认路径。
- 多 Worker 当前 A 只快约 24%、B 反而慢约 11%；继续默认关闭。检查点重复解码、分块保存和多 Worker 都只保留隔离实验资格。

### 7.3 决策

**M-1 = GO，允许进入 M0，并在诊断开关下开始 M1；默认引擎替换 = NO-GO。**

通过依据：正式冷基线、raw-cache dev/preview 各 3/3、两档 production-preview 旅程、≥95% 物流归因、命令与工作负载矩阵、profiler 扰动、1x/4x/11x、两档 30 分钟内存/CPU trace 和长时 pending debt 基线全部有可重复证据；运行时代码与测试在 clean `58456b391c4311c0a4969cfe7075c0f47bc75b12` 冻结。

当前明确不能承诺：5～50 倍长时加速、55% 完整周期收益、30d 真实档已完整精确结算、多 Worker 默认启用、WASM/Rust 重写、增量存档进入稳定版。只有后续每个里程碑在同机两档完整周期与旧引擎逐字段 oracle 同时通过，才能升级这些结论。
