# 1.3.3 后网页启动入库诊断与后台原型

状态：性能循环已经恢复。本轮完成根因复测和隔离原型，不修改游戏运行源码，不发布。香港仍使用 `1.3.3+a0fd77efc399`。服务器、真实存档及服务器自动备份停用配置均未操作。

## 已确认的瓶颈

对实际发布的 1.3.3 页面完成两次真实大档旅程：普通运行积累统计 → 产率复制 → 停止 → 校验保存。为实验开启主线程 IndexedDB 调用观测，默认不开启。两次最长启动任务分别为 1,176 ms、1,179 ms；对应 `put()` 同步调用分别为 1,176.30 ms、1,178.90 ms，时间窗重合。第二次同时记录库名，确认为 `dsp-idle-network.pure-idle-recovery` 的 `records` 对象仓库。

这一秒主要消耗在恢复日志的大对象入库调用中，发生在普通 T0 检查点之前。观测的是 `put()` 返回前的同步复制/编码成本，不是异步磁盘事务总耗时。主线程 `IDBRequest.result` getter 的已观测最大开销约 0.1 ms；这也不代表完整读取旅程只需 0.1 ms。

两次页面旅程都完成，保存完整性为 `valid`，实体 110,042、传送带 233,300，停止后恢复暂停，`autosaveIntervalSeconds = 0`。本轮没有移除普通 T0，也没有重新启用曾否决的跳过检查点变体。

## 隔离原型的数字

原型直接调用现有 `createPureIdleRecovery`，仍使用现有恢复库、原子事务、状态格式和校验逻辑。对照使用主线程调用；后台方案先分批交接冻结状态，再在独立 Worker 中调用同一函数。每批最多 512 个实体或 2,048 条传送带，上一批确认后才发送下一批。

每种方案各两次，均为全新隔离浏览器；首轮顺序为主线程、后台、后台、主线程。以下是两次的中位数，**只测这一步写入及其交接，不是整页启动或全游戏性能**。

| 指标 | 现有主线程写入 | 后台，每批另让出任务 | 后台，按确认逐批发送 |
| --- | ---: | ---: | ---: |
| 最长画面间隔 | 1,310.30 ms | 34.75 ms | 7.10 ms |
| 最长间隔减少 | — | 97.35% | 99.46% |
| 写入与交接总时间 | 1,333.80 ms | 2,238.15 ms | 2,164.90 ms |
| 总时间变化 | — | 增加 67.80% | 增加 62.31% |

按确认逐批发送的两次传输分别为 838.20、840.50 ms，事务完成等待为 1,327.00、1,324.10 ms；主线程单次发送最长为 2.20、1.90 ms。这说明后台方案能明显减少界面冻结，但独立增加一次整档交接仍带来约 0.83 秒额外等待。不能据此宣布整个游戏已经丝滑，也不能宣传游戏快了 99%。

## 继续开发的门槛

优先验证能否与现有开始检查点共用已交接的冻结状态，减少额外传输和临时副本。接入正式启动流程前，需要保留主页面持有的写入权，验证取消、关闭页面、Worker 崩溃、配额不足及多标签页强制接管；旧 Worker 的迟到写入不得覆盖新会话。原型在隔离 Worker 中自己取得写入锁，不能直接照搬到主页面已经持锁的生产路径。

之后必须比较真实整页的启动总时间、最长停顿及全部相关进程内存，完成正式代码的完整持久化回归。普通 T0、现有存档格式、材料/时间结算规则以及备份关闭设置都必须保留。当前只是已确认根因和可用的响应性方向，正式接入尚未完成。
