# 排行榜资格状态 UI 缺陷与人工复核交接

> Role: feedback
> 日期：2026-08-11
> 状态：只读分析完成；未修改产品代码、生产数据库、云存档或排行榜历史

## 1. 任务信息

- Task ID / title：排行榜资格状态与可见性开关分离
- Priority：P1（账号控制显示错误；无云存档数据丢失）
- Source and attachments：玩家截图 `codex-clipboard-55d721fa-2d99-4eb5-9951-3ed998becc2b.png`；显示名称“作者”
- Target platforms：Web、PWA、Windows、Android；80%～200% 字号和桌面/移动布局
- Release target and version：下一开发版本；生产人工复核目标节点尚未确认

## 2. 已确认现象与原因

1. `leaderboardVisible` 只表示玩家主动选择公开或退出，不表示账号是否具备排行榜资格。
2. 服务端另有只存在内部数据中的 `leaderboardModeration[userId]`。`blocked / SAVE_DATA_INTEGRITY` 账号可以继续登录和同步云存档，但重新开启排行榜会收到 `403 / LEADERBOARD_RESTRICTED`。
3. 历史处置没有把 `leaderboardVisible` 同步改为 `false`，所以受限账号仍可能先看到开启状态；玩家关闭后，重新开启才暴露服务器限制。
4. 前端失败后保留服务端 `leaderboardVisible=false`，开关因此立即弹回关闭。
5. 错误只渲染在“银河排行”页签，截图所在“账户”页签没有提示；账户页仍把状态显示为普通主动退出，形成错误暗示。
6. 显示名称“作者”只是可修改的公开名称，不是管理员角色，也不能覆盖由不可变服务器账号 ID 关联的资格状态。

## 3. UI 状态模型

前端必须明确区分下列状态，不能继续只依赖一个布尔值：

| 可见性 | 资格 | UI 状态 | 是否允许玩家自行切换 |
| --- | --- | --- | --- |
| `true` | `eligible` | 参与公开排行榜 | 可以关闭 |
| `false` | `eligible` | 玩家主动退出排行榜 | 可以重新开启 |
| 任意 | `restricted` | 排行榜资格受限，等待人工复核 | 不可以 |
| 任意 | `revalidation-required` | 已批准复核，等待新的合法主云修订 | 不可以直接入榜 |
| 未知 | 请求失败 | 无法确认排行榜状态 | 保留最后确认状态，不做乐观提交 |

推荐由 `/api/account` 返回不含内部原因的安全派生状态，例如：

```text
leaderboardEligibility: eligible | restricted | revalidation-required
leaderboardVisible: boolean
```

不得返回内部 `reasonCode`、审计来源、时间戳、检测阈值、关联账号或存档异常细节。旧客户端缺少新字段时继续按现有布尔值运行。

## 4. 用户界面需求

1. “账户”和“银河排行”两个页签必须显示同一权威状态与同一错误信息。
2. 普通主动退出时显示“已退出排行榜”，辅助文案可写“可随时重新加入”。
3. 资格受限时显示“排行榜资格待人工复核”，辅助文案写“公开排名不可用，云存档仍正常同步”；开关禁用，不能伪装成可操作状态。
4. `LEADERBOARD_RESTRICTED` 返回后，当前页立即进入受限状态并以 `role=alert` 显示通用说明，不要求玩家切换页签才能看到。
5. 已批准恢复但等待新修订时显示“请上传新的主云存档修订完成重新验证”，不能宣称已经恢复排名。
6. 网络失败、超时和未登录要与资格受限使用不同文案；失败时不能偷偷改本地隐私状态。
7. 不显示检测规则或可帮助绕过完整性检查的细节。
8. 桌面、移动、触摸、键盘和 80%～200% 字号下状态、说明和操作必须可见、可聚焦且不溢出。

## 5. 数据与兼容性约束

- 不修改 `GameState`、存档 envelope、云存档 schema 或 SQLite layout。
- 排行榜资格继续以服务器账号 ID 为权威，不能按显示名称判断。
- UI 修复不能修改、补写或删除排行榜历史成绩。
- 资格受限和重新验证期间，登录、云存档上传、下载、历史恢复和账号导出保持可用。
- 普通模式和速通模式共用账号资格，但各自存档及排行榜提交仍按现有规则隔离。

## 6. 必须新增的测试

1. 普通账号关闭后可重新开启并从当前主云档回填。
2. 受限账号开启请求返回 `LEADERBOARD_RESTRICTED`，开关保持关闭。
3. 受限提示在“账户”和“银河排行”页签都可见。
4. 受限状态不显示“可随时恢复”，也不显示内部原因码和审计细节。
5. 刷新、重新登录和跨设备后受限状态保持一致。
6. 人工批准后进入 `revalidation-required`，旧修订不能重新入榜。
7. 上传更高且通过完整性校验的主云修订后才清除重新验证门禁。
8. 受限、待重新验证和主动退出期间云存档同步均正常。
9. 网络失败和 401 不得误显示为资格受限。
10. 普通排行榜与速通排行榜都遵守同一账号资格门禁。
11. 390×844、桌面宽屏、80% 和 200% 字号下状态与提示可见可操作。

## 7. 用户可见验收标准

- 玩家能立即分辨“自己退出”和“服务器资格受限”。
- 点击失败时当前页面直接说明原因，不再出现无提示弹回。
- 受限玩家明确知道云存档没有被删除或停止同步。
- 普通玩家关闭后仍可正常自行恢复。
- UI 不泄漏内部反作弊规则，也不产生绕过资格限制的入口。

## 8. 当前账号人工复核的已知证据

仓库只保存脱敏审计结论，截图本身不能证明显示名称“作者”与内部限制记录是同一账号。若经不可变账号 ID 确认是同一记录，历史审计证据为：

- 数据库、云档正文、SHA-256 和 envelope 校验均完整，不是存档文件损坏。
- 39 个矿脉实体的 `machineCount` 非零，合计约 13.90 亿；官方玩法只会增加矿脉的 `minerCount`，不会增加 `machineCount`。
- 高阶建筑库存的最低白糖成本约 7.300 万亿，而存档累计生产白糖约 6.106 亿，守恒缺口约 1.20 万倍。
- 异常字段和高阶库存模式还出现在关联存档中，因此当时按服务器账号 ID 写入持久资格限制。

上述证据不能证明玩家主观意图，但足以说明不能仅凭“这是作者账号”直接恢复官方排名。

## 9. 人工恢复的安全门禁

执行角色必须为 release/operations，并取得明确节点授权。当前缺少目标节点、不可变账号 ID 和可独立检查的当前主云存档，因此不能执行生产写入。

1. 只接受精确内部账号 ID；禁止按“作者”等显示名称直接操作。
2. 先创建并验证当前节点 SQLite Backup API 备份，记录 `quick_check=ok` 和回滚位置。
3. 在只读副本核验当前普通模式主云档的 revision、正文 SHA-256、envelope、状态校验及全部保留历史。
4. 重新检查矿脉 `machineCount`、非负安全整数、内容包/MOD 状态、建筑来源和关键材料守恒。
5. 若当前档仍含异常，停止恢复；不得删字段、补物资、清缓存或直接改排行榜来通过。
6. 只有人工复核明确批准后，才能调用受保护的 `restore-leaderboard` 管理动作；该动作必须写入匿名审计，并要求一个高于当前 revision 的新主云修订重新验证。
7. 新修订通过现有服务端完整性门禁后，由服务端从当前主云档重新计算排名；禁止直接插入或修改历史 submission。
8. 复核五个普通榜和三个速通榜、云存档上传/下载/历史恢复、服务重启回填及其他同名账号均未受影响。

## 10. 回滚

- UI 变更可回滚到改动前客户端，不触碰服务器数据。
- 人工恢复出现异常时，先重新限制该精确账号并移除新生成的公开 submission；保留当前数据库和事前备份，不直接恢复旧数据库。
- 玩家云存档正文和历史修订不属于排行榜资格回滚范围，任何情况下都不得删除或覆盖。
