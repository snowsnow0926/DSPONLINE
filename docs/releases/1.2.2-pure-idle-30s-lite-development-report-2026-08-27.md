## 1. 结论

1.2.1 大存档进入保守纯挂机时只精确观察 1 个模拟秒。慢配方、线路暖机、分批物流或在第一秒没有完成品的白矩阵产线，会被误判为零；此前为了防止戴森结果凭空增长，保守尾段又整体冻结，所以玩家看到“纯挂机全是 0”。

1.2.2 恢复了玩家希望的宏观外推，但不恢复旧实现的多份完整状态内存成本：

- 连续精确运行 30 个模拟秒，分别记录 0、10、20、30 秒四个轻量快照；
- 普通生产和科研可以按三个窗口的真实结果外推，20 秒等慢周期配方不再被第一秒误判；
- 快照只含累计生产、行星/量子库存、建筑输入和输出，不复制线路、坐标、诊断、界面状态和完整循环相位；
- 每种净消耗物料单独计算可支撑时长，并沿正在工作的配方向下游传播；一条支路耗尽只停止受影响产物；
- 小型运载火箭、太阳帆、戴森结构/壳面、银河出口、合同和巨构交付只提交精确 30 秒前缀，不在没有闭合账本时复制终局成绩；
- 候选失败、取消或超时仍丢弃候选并保留原检查点，不会部分写入。

这不是逐秒重放整个挂机区间，因此仍然是低资源的宏观近似；目标是“普通产量大致正确且快速”，不是让所有瞬时物流位置与在线运行逐字节一致。

## 2. 为什么 30 秒可以解决一秒样本的问题

一秒样本只回答“这一秒有没有成品”。它无法区分：

1. 产线停了；
2. 配方需要 20 秒，第一秒只是累计进度；
3. 线路刚启动，物料还在路上；
4. 产线正在短暂吃旧缓存，马上就会缺料。

三段十秒观测可以看见慢配方真正完成，也能比较启动段和后两个窗口是否趋于稳定。外推使用的是已经发生的产量，不读取建筑面板上的理论满速；因此堵塞、断电、低供电和停止生产会自然反映到样本里。

与此同时，外推不能只复制累计生产数字。若某原料在 30 秒内净减少，系统会用“校准结束时全部聚合库存 ÷ 实测净消耗速度”计算该原料还能支撑多久。物料所有权聚合覆盖行星托盘、建筑输入输出、物流站和航线、量子库存、施工任务库存等位置，并避免把同一份物料重复计数。

## 3. 真实玩家存档只读实测

测试附件：`D:\360安全浏览器下载\dsp-idle-save-2026-08-26.json`。

- 文件大小：44,167,989 字节；
- GameState v47 / envelope v2，检查有效；
- 45,904 个实体、91,955 条线路；
- 15× 时间扭曲、无限资源模式；
- 结算窗口：真实时间 600 秒，即目标模拟时间 9,000 秒。

| 指标 | 实测结果 |
| --- | ---: |
| 30 模拟秒校准白矩阵增量 | 1,141,066,480 |
| 10 分钟真实时间最终白矩阵增量 | 166,367,492,784 |
| 10 分钟窗口平均白矩阵产量 | 277,279,154.64 / 真实秒（约 2.77 亿/秒） |
| 精确前缀火箭增量 | 23,804,542 |
| 校准耗时 | 30,459 ms |
| 宏观尾段结算耗时 | 2,545 ms |
| 序列化、inspectSave 与重载 | 2,384 ms |
| 整项测试耗时 | 40,732 ms |
| 测试结束 Node heap used | 约 858 MiB |

最终白矩阵增量不是简单把 30 秒结果无条件乘到 9,000 秒。部分支路在样本中表现为净消耗缓存，达到各自物料边界后停止获得外推额度；仍有持续来源的生产继续，所以结果既明显大于零，也不会把一次性缓存当成永久供应。

火箭增量只来自精确执行的 30 模拟秒。尾段没有复制火箭发射或戴森结构，因此本修复不会重新引入 1.1.8/1.1.9 曾出现的戴森球凭空增长问题。

测试前后玩家附件的文件大小、修改时间和 SHA-256 均未改变；测试只在隔离内存副本中运行。

## 4. 确定性与安全边界

新增回归覆盖：

- 1 秒无产出、20 秒才完成的慢配方在 30 秒样本后可形成非零外推；
- 预填缓存而上游不足时，产物不超过聚合物料来源；
- 8×、12×、15×、16× 下，单次长结算与多段结算一致；
- 无限与有限资源、多恒星系目标、太阳帆轨道；
- 库存耗尽、输出堵塞、断电、低供电和停止生产；
- 候选失败、取消、Worker 重启和保存失败时源状态不变；
- 序列化、重载和 `inspectSave()` 后守恒继续成立；
- 发射井预填火箭不能在尾段被重复复制。

仍然明确冻结的尾段包括：火箭和太阳帆制造/发射、戴森结构与壳面、银河出口、空间站合同和巨构交付。后续只有在这些系统拥有各自闭合的“期初库存 + 生产 - 期末库存 = 消耗/交付”账本后，才可以安全开放对应外推。

有限矿脉的剩余储量不在轻量库存快照中。只要校准开始时存在正在工作的有限矿脉，本版保留精确 30 秒收益并冻结宏观尾段，宁可少结算也不跨过矿脉耗尽边界造物。

## 发布角色复验补充

发布前单线程复验首先得到 428 通过、27 条条件跳过、3 失败；三条失败在全新浏览器中各连续复跑 3 次均通过，随后同一 458 项矩阵按四个独立浏览器分片重跑为 431 通过、27 条条件跳过、0 失败。失败根因是超长单浏览器进程的资源累积，不是产品回归。

生产预览中的 500 节点画布门禁随后暴露出独立的统计稳定性问题：144 Hz 下每轮只有约 34 个 rAF 样本，两个 27.8 ms 的量化帧就会把单轮离散 P95 推高到 27.8 ms。完全相同的 1.2.1 基线在同一主机也复现，且 1.2.2 没有改动画布产品路径。门禁因此改为汇总三次相同手势的全部样本计算总体 21 ms P95，同时继续要求每轮最大帧不超过 100 ms；没有放宽产品阈值，也没有修改运行时代码。

## 6. 发布建议

1. 1.2.2 可以作为纯挂机快速修复候选，重点解决 1.2.1 保守大档“第一秒没成品就整段为零”的问题。
2. UI 应把结果描述为“30 秒实测宏观估算”，不承诺与在线逐秒运行完全相等。
3. 终局系统继续显示精确前缀产量，不应把冻结尾段伪装成理论产量。
4. 正式发布仍需 Release Agent 在固定 clean SHA 上重新生成候选清单、签名/未签名标识和最终制品；本开发分支不自行部署。
