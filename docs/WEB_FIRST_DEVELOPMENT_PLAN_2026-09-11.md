# 网页版优先：性能、功能与交付计划

日期：2026-09-11。计划 ID：WEB-FIRST-20260911。

用户已决定放弃 Windows 本地版主导的开发路线，后续以网页版为主。本文件替代旧 Windows/Rust 计划的当前执行优先级；历史实现、分支、测试和测量保留。本轮只进行代码审阅与规划，不开发新功能、不部署、不启动持续循环 Goal。

## 1. 产品方向

| 平台 | 后续定位 |
| --- | --- |
| 网页版 / PWA | 主产品与性能验收入口。桌面浏览器和手机浏览器都纳入场景，按真实使用数据确定设备投入。 |
| Android | 复用同一套玩法、画布和大部分性能优化；重点维护 WebView、生命周期、导出、更新与覆盖升级。共享代码仍须分别验证。 |
| Windows 本地版 | 保留既有代码、下载、存档兼容及必要修复；停止以完整原生接管、Windows 专属功能齐套作为当前目标。 |
| Rust | 保留算法、确定性测试和对照工具；仅在网页真实热点有明确收益时，评估小范围 Wasm。 |

以后用“玩家能否更快进入游戏、操作是否流畅、保存是否可靠、工厂是否容易管理”衡量进度。Windows Rust 功能覆盖率不再作为项目主线进度指标。已经上线的共享优化继续使用；不卸载、删除或清理旧客户端和玩家数据。

## 2. 当前进度的判断

基线是已发布的 **1.2.9+0521eb63f179**，GitHub main 收口提交 `b7fd8f1b`。以 [发布记录](./releases/1.2.9.md) 为证据，没有在本次规划中重新测量性能或查询生产玩家数据。

**已具备的基础：**

- 网页与安卓共享保存、自动快照、模拟准备优化；WASD、生产区域/节点一起移动和手机结算报告修复已上线。
- 已有常驻模拟 Worker、命令与 revision 协议、当前星球投影、差量/分块传输、主档回读、fencing/CAS、目录惰性读取与恢复机制。
- 已有画布快照、节点 memo、细节降级、连线批量绘制与空间索引。后续要优化实际命中路径，不能把“增加 Worker”“做虚拟化”当作全新方案再开发一遍。
- 已有生产管理、来源追踪、物流诊断、蓝图和区域编辑；区域总览建议建立在这些功能上。

**仍有证据缺口：**

- 4.1 MB 公开合成档的主档 ACK 中位数降低 32.4%，只证明一个保存步骤；没有网页版整体提速比例。约 108 MB 终局档的正式性能对比受内存保护停止。
- 最终源码单元 3,183 通过；完整本机浏览器加原断言补验覆盖 461 个不同用例，33 条件跳过。云端仍保留 4 个失败和 2 个不稳定用例，不能宣称整个质量链已收口。
- Android 有最终包直接升级与保存重开证据，但没有实体手机长时、发热、耗电结论。旧匿名 AVD 的损坏原因也未确定。
- 网页场景中，模拟、投影/传输、React/绘制、序列化/持久化各占多少耗时尚未形成统一的大档报告。源码结构能指出候选热点，不能代替 profile。

因此，现阶段是“已经能交付共享改进，仍需围绕实际瓶颈收敛”。不以一个缺乏统一分母的“完成百分比”描述整个性能工程。

## 3. 为什么调整方向能减少无效投入

Windows 全量 Rust 路线同时承担第二套运行时、IPC、状态权威、文件/WAL、崩溃恢复、UI 命令覆盖和安装器验收。它们是实际工程工作，但大量投入需要等完整闭环后才触达网页版玩家。

1.2.9 已证明，共享路径的小步优化可以直接交付网页与安卓。继续采用现有 JS/TypeScript 与 Worker 架构，每次解决一个有测量依据的瓶颈，更容易持续发布。旧 Rust 工作中的算法、状态对照和恢复经验仍有价值；Windows Host、原生文件系统和 IPC 工作不再占据主线。

另一个成本来自交付流程：1.2.9 的完整本机浏览器测试耗时 26.8 分钟，另外发生版本环境、悬浮操作、异步缓存等待及发布脚本绑定问题。网页版 UI 的 CI 目前也会编译 Rust Host 并运行完整原生套件。需要按受影响范围整理测试和发布入口，同时保留发布所需的完整适用矩阵。

## 4. 优先优化的五条路径

| 玩家体验 | 已有基础 | 下一步重点 | 验收证据 |
| --- | --- | --- | --- |
| 打开网页、继续游戏 | 懒加载、存档目录索引、PWA 版本隔离 | 区分菜单出现、工厂可操作、离线资源准备三个时刻；检查重复检查/读取及 PWA 预缓存成本 | 冷/热启动到可交互时间、下载字节、长任务；更新后离线仍可进入支持的场景 |
| 拖动、缩放、框选 | 画布快照、memo、连线缓存与细节降级 | 测量并减少无关组件刷新、全量扫描与几何重建；将交互动画和数值刷新分开 | 固定大档、固定视口的输入延迟、P95 帧耗时、最长卡顿、选中/移动正确性 |
| 保存、导入、回到菜单 | Worker proof、回读、快照复用、分块协议 | 查明仍重复生成的完整副本及等待链；复用已验证中间结果；明确保存失败的可重试状态 | 完整等待、峰值内存、主档/备份一致性；失败不回档、不误报成功 |
| 长时间挂机、切后台再回来 | 可取消离线、冻结边界、恢复日志 | 覆盖隐藏、休眠、标签页丢弃、断网和重开；降低非必要后台显示工作 | 结算只提交一次、可取消、旧主档有效；恢复后库存和时间连续 |
| 大工厂模拟本身 | 持久 runtime、索引、空阶段跳过 | 仅根据 profile 优化最热阶段，减少重复扫描与分配，评估已有批处理适用范围 | 相同输入和时间的完整结果相同，端到端更快，其他模式不回退 |

视口限制只影响显示工作。其他星球和屏幕外机器仍按原规则生产；不能靠少算模拟秒、跳过产线或修改倍率来换帧率。显示刷新频率可以按设备和交互状态调整，结算频率与规则须保持正确。

React Flow 官方文档同样建议减少无关重渲染、缩小状态订阅并控制复杂样式；本仓库已有部分实现，需测量剩余成本后再改。[React Flow 性能说明](https://reactflow.dev/learn/advanced-use/performance)

`ArrayBuffer` 转移能避免对应缓冲区复制，但编码、解码、扫描和构造对象的成本仍需分别测量。仓库已经使用 transfer，下一步应排查剩余复制而非机械地增加更多线程。[MDN Transferable objects](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Transferable_objects)

## 5. 功能优先级

优先做降低管理负担、能在同一份共享代码中交付的功能。下列内容是建议，未开始实现，也没有新建大系统的授权推断。

**第一优先：生产区域总览。** 在现有区域边框与联动选择基础上，提供区域列表、定位和汇总：机器数量、实际产出、净耗电、主要缺料/堵塞。先定义跨区线路、边界节点、重叠区域的统计口径；保留区域成员的现有几何语义，不在未经设计时引入持久成员表。汇总按 revision/成员变化缓存，避免每帧全厂扫描。

**第二优先：把现有诊断变成明确行动。** 复用生产管理的缺料、堵塞、供电和来源追踪，增加从区域/异常摘要定位到具体节点的路径，让玩家知道“先改哪一处”。不重复开发另一套产量或供电计算。

**第三优先：批量操作的可预期性。** 基于现有选择/蓝图/待建流程增强过滤与操作前预览，明确影响哪些节点、材料是否足够、哪些被锁定，并维持一次撤销。先做一个高频动作，不把批量配方、自动布线、区域模板和蓝图市场同时塞进一版。

**持续优先：保存与恢复的清晰提示。** 利用已有状态区分“内存中的进度”“本地已写入”“云端已同步”；确认失败时保留可操作的恢复入口。已有导出、冲突比较、备份和存储提示应完善，不重新做同名系统。实际丢档、重复结算、无法进入游戏的问题随时提升为 P0/P1，优先于功能。

暂不扩展战斗、大型新玩法、多人服务器权威或另一个客户端 UI 框架。

## 6. 分阶段交付与工程量

下表为**各阶段新增工程人日**，包含实现、联调、相关回归和一次交付准备；不是累计数，也不是 AI 连续运行小时数或保证的日历工期。估算置信度中低，设备/反馈等待另计。阶段 0 完成后按实际热点重新估算。

| 阶段 | 内容与玩家交付 | 初估 | 次序 |
| --- | --- | --- | --- |
| 0：基线与交付整理 | 固定 1.2.9 对照、定位瓶颈、整理易错测试入口与版本来源，产出一个明确的优化任务 | 1–2 人日 | 先做；不是单独的性能提升版本 |
| 1：首个网页收益版 | 默认从画布/进入工厂热点中选一项，修复关联稳定性问题，并给出真实前后对比 | 3–5 人日 | 建议作为 1.2.10 候选范围 |
| 2：大档保存与恢复 | 降低保存/导入/离线恢复的等待或峰值内存，完成后台与重开闭环 | 4–7 人日 | 接续；若阶段 0 证明它是主要问题，可提前 |
| 3：区域管理体验 | 区域总览最小闭环、异常定位；只纳入一个必要的批量操作增强 | 3–5 人日 | 在主链稳定后；小功能可随阶段 1/2 提前交付 |
| 4：剩余模拟热点 | 按占时优化最热的模拟阶段、索引或批处理 | 5–10 人日 | 条件阶段；若模拟占主要时间，则提前并重估 |
| 可选：Wasm 验证 | 只选一个独立计算段，验证编译、状态等价、冷启动与传输开销 | 2–4 人日 | 前述测量支持后才做；正式接入另估 |

阶段 0+1 合计 **4–7 人日**，目标是拿到第一版可验证收益；前 0–2 阶段合计 **8–14 人日**。不是要求等所有阶段完成才发布，也不能把所有上界当作固定总工期。

一个版本原则上只承载一个主要性能目标、一个小功能和必要稳定性修复。每个目标分别提交，能独立验收。没有改善或收益太小的试验保留结论并停止扩展，不把代码量记作收益。

## 7. 阶段 0 与首版的具体执行单

1. 以 tag `v1.2.9` 的真实运行源码和公开制品为对照，核对所测构建 ID。保留小/中档、4.1 MB 合成档及大档梯度；授权终局档只在满足内存预算时测试副本，绝不上传到生产或进入制品。
2. 复用 `performanceHarness`、Worker profiler 与现有监控。分别记录菜单可见、工厂可操作、模拟耗时、投影/传输、主线程绘制、保存 ACK、完整保存/重开、峰值内存和失败原因。
3. 测暂停平移/缩放、运行中平移/框选、打开统计、保存返回、离线结算/取消/重试、更新/断网重开。固定总实体数、可见数量、画布缩放与刷新策略，不能只比较文件大小。
4. 清理已确认的测试环境与时序问题：统一 npm 入口和版本变量；正确处理附带报告和动画完成；使用明确异步完成条件；功能失败与性能超阈值分开保留，不能靠提高门槛变绿。
5. 发布元数据统一取自 manifest，覆盖 Web、安卓包、下载页标题、链接、大小和哈希；旧节点/旧版本差异由显式 profile 描述，避免复制历史脚本后漏改常量。先 dry-run 和独立内容核对。
6. 根据证据只选择一个主要瓶颈实施。默认候选是画布刷新与投影；若 profile 显示主要时间在模拟或存储，就调整顺序。

阶段 1 拟定收益门槛：固定设备、相同有效工作量的目标场景，在至少三组配对正式样本中，端到端等待或 P95 帧耗时改善约 20% 以上；这是筛选目标，不是已实现成绩。其他关键场景须无稳定可复现回退，完整状态与保存安全检查必须通过。旧 500 ms 等已有门槛不因本计划自动放宽。

如果只减少 Worker 内核时间而玩家等待没有改善，不能宣传为该场景加速。只改善显示流畅度时，也不能宣传为生产速度提高。

## 8. 浏览器的边界与 Rust 的位置

浏览器会限制后台页面的动画和定时器，设备也可能挂起页面。因此产品目标应是“暂停显示工作、保存检查点、回来正确补算”，不承诺浏览器锁屏后一直满速计算。[MDN Page Visibility](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API)

浏览器存储默认受容量与回收策略约束。已有持久存储申请、导出与云档需要形成清晰的恢复体验；更换成另一种浏览器存储 API 不会自动解决所有数据风险。本阶段不迁移公开存档格式或直接替换 IndexedDB。[MDN 存储配额与回收](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)

Wasm 可以作为以后的计算加速工具，但不是把 Windows Host 直接放进网页。当前 core 依赖 Rayon、Host 有文件系统和 Windows API；Rust 的普通 `wasm32-unknown-unknown` 目标没有可直接照搬的 OS 文件/线程能力。需要逐个模块检查依赖、数值顺序和 JS/Wasm 数据边界。[Rust Wasm 目标说明](https://doc.rust-lang.org/rustc/platform-support/wasm32-unknown-unknown.html)

首个 Wasm 试验应为 Worker 内的一个有界纯计算段，保留 JS 对照与能力回退，不引入第二份持续双算的正式状态。先评估单线程；浏览器共享内存涉及 COOP/COEP 等隔离约束，需要同时验证主站、独立上海、安卓资源与账号跳转，不能直接复制 Windows 线程池策略。[MDN 跨源隔离](https://developer.mozilla.org/en-US/docs/Web/API/Window/crossOriginIsolated)

当 profile 证明一个独立内核长期占主要等待，且计入下载、初始化、编解码、传输后仍有显著收益，才升级为正式 Wasm 接入项目。2–4 人日的试验只回答“值不值得”，不承诺完成跨端 Rust。

云 API 的延迟、云存档上传和服务端阻塞是另一条性能路径。本版一次香港 health 9.17 秒后恢复，原因仍需证据；增加服务器资源不会直接提高运行在玩家浏览器内的模拟速度。没有新证据时不把它当作网页模拟重写理由。

## 9. 验证、交付与停止条件

- 开发时按变化运行必要检查；发布前完成完整的**适用**矩阵。Web 发布检查 Web、共享玩法/存档及 API 契约；触及共享引擎/原生桥时纳入对应 Rust/原生检查。测试拆分必须先说明覆盖归属，不能直接删掉原生测试。
- Android 改包后核对正式端点、长期签名和覆盖升级；有条件补实体 Android 设备。新性能宣称按实测设备给范围。Windows 未变的安装器不反复启动，也不将其完整原生接管门禁绑定到每次网页小改动。
- 背景、无声、不抢焦点测试；重任务串行、受资源预算约束。保护触发时记录失败/未测，不计作通过，也不关闭用户其他程序。
- 保留同状态同时间确定性、库存和研究等进度、旧档与内容包、锁定、多标签页写入权、一次结算、取消与失败重试。数据正确性失败立即停止该候选。
- 香港与上海独立发布；代码回退不回退玩家数据。小版本不默认开启新的耐久、原生或近似结算资格。
- 当前没有活动 Goal；本计划不启动定时器、自动开发循环或发布。下一次开发从阶段 0 和首个测量支持的共享热点开始。
