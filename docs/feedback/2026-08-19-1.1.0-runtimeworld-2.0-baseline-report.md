本报告是 [1.1.0 RuntimeWorld 2.0 开发计划](../1.1.0_RUNTIMEWORLD_2.0_DEVELOPMENT_PLAN.md) 的实测依据。它刻意把已确认事实、推算和未来目标分开，避免把局部提升错误地当成整款游戏的提升。

调研期间仓库前进了三个仅涉及发布说明 UI 和另一条 E2E 等待条件的提交；本报告涉及的引擎、Projection、存储与两份真实档基准代码未随这些提交变化。文档统一记录调研结束时的 HEAD。

## 1. 小白先看结论

当前架构并不是“整份几十 MB 存档每秒都发给界面”。现有 Projection 已经把每次传输压缩了约 **99.3%～99.6%**，这一层做得很好。

真正的大头是游戏规则计算：生产、传送带、物流和电力合计占两份真实档模拟时间的 **84.2%～87.3%**。所以 RuntimeWorld 2.0 应优先改变模拟内部的数据结构和算法。

用“原来每次要等 100 秒”来理解本计划：

| 级别 | 100 秒预计变成 | 耗时下降 | 速度约为原来的 |
| --- | ---: | ---: | ---: |
| 1.1.0 最低放行线 | 60 秒以内 | 40% 以上 | 1.67 倍以上 |
| 1.1.0 正式目标 | 45 秒以内 | 55% 以上 | 2.22 倍以上 |
| 冲刺目标 | 37 秒左右 | 约 63% | 约 2.7 倍 |

这些是依据当前各阶段占比计算出的工程门槛，不是已经实现的结果。两份真实档都达到最低线，才能把 RuntimeWorld 2.0 称为 1.1.0 的有效底层升级。

## 3. 当前模拟基线

### 3.1 60 秒精确模拟

同一状态分别执行“一次推进 60 秒”和“连续推进 60 次、每次 1 秒”。两条路径的玩法哈希一致，非法库存数量为 0。

| 指标 | A：36.7 MB | B：10.0 MB |
| --- | ---: | ---: |
| 一次精确推进 60 秒 | 35,663 ms | 9,519 ms |
| 逐秒推进 P50 | 543 ms | 162 ms |
| 逐秒推进 P95 | 816 ms | 242 ms |
| 逐秒推进最大值 | 862 ms | 338 ms |
| 物资合法性 | 0 个非法值 | 0 个非法值 |
| 60 秒玩法哈希等价 | 通过 | 通过 |

通俗解释：A 档的 Worker 虽然还能跟上普通 1 倍时间，但每次工作常常占用半秒到近一秒；高倍精确挂机和需要等待权威回执的操作会明显受限。B 档约快 3.7 倍，但逐秒 P95 仍达到 242 ms。

### 3.2 时间花在哪里

| 模拟阶段 | A 占总模拟耗时 | B 占总模拟耗时 |
| --- | ---: | ---: |
| 生产设备 | 32.0% | 10.2% |
| 传送带 | 31.7% | 32.9% |
| 物流 | 11.8% | 30.1% |
| 电力 | 11.8% | 11.1% |
| 量子物流 | 3.7% | 7.1% |
| 前四项合计 | **87.3%** | **84.2%** |

已确认结论：

1. 传送带在两份档中都约占三分之一，是最稳定的首个 RuntimeWorld 迁移对象。
2. A 更受生产设备影响，B 更受物流影响；只优化一种玩法不能普遍获得巨大提升。
3. 生产、传送带、物流、电力必须共用新的紧凑运行时和唤醒机制，才能接近 40%～60% 的整体下降。

## 4. Projection 与主线程镜像基线

本组在稳定运行后连续采样 8 次，把一次更新拆为：模拟前基线扫描、引擎推进、变化构造、Projection 编码、UI 镜像应用。

| 每次 1 秒推进的平均值 | A：36.7 MB | B：10.0 MB |
| --- | ---: | ---: |
| 模拟核心 | 628.2 ms | 198.1 ms |
| Projection 基线扫描 | 15.7 ms | 14.1 ms |
| Projection 差异构造 | 56.5 ms | 23.3 ms |
| Projection JSON 编码 | 2.0 ms | 0.5 ms |
| UI 镜像应用（不含 React 绘制） | 11.3 ms | 2.3 ms |
| 合计 | 713.7 ms | 238.3 ms |
| 扫描 + 差异占比 | **10.1%** | **15.7%** |

| 传输指标 | A | B |
| --- | ---: | ---: |
| 完整运行态 JSON | 48.1 MB | 18.0 MB |
| 平均 Projection | 0.357 MB | 0.081 MB |
| 相对完整状态减少 | **99.26%** | **99.55%** |
| 活动行星变化实体占比 | 23.3% | 7.5% |
| 活动行星变化线路占比 | 99.3% | 12.2% |

已确认结论：

- Projection 的传输大小已经不是主要问题。
- Dirty Journal 仍值得做，因为它是 RuntimeWorld、事件队列和增量保存的共同基础；但单独做它，整周期合理上限只有约 **6%～13%**，不能再宣传为 20%～60% 的整局提升。
- A 档几乎所有活动行星线路每秒都变化，仅靠“跳过没变化的线路”不会产生奇迹；需要改变线路计算的数据布局和算法。
- UI 镜像只保持活动行星精确，非活动行星按现有协议延迟刷新；活动行星实体和线路逐字段核对一致。

## 5. 稳定生产链 / 事件驱动潜力

仓库现有影子分析器会深比较通用 JSON 对象树。它只适合调研，不能直接进入产品。

| 指标 | A：4 秒观察 + 4 秒验证 | B：12 秒观察 + 12 秒验证 |
| --- | ---: | ---: |
| 可识别最大周期 | 1 秒 | 4 秒 |
| 预测不一致 | 0 | 0 |
| 已验证稳定实体 | 7,268 | 4,917 |
| 已验证稳定线路 | 10,317 | 6,476 |
| 保守引擎耗时下降推算 | 11.7% | 27.3% |
| 乐观引擎耗时下降推算 | 16.1% | 43.2% |

A 档的 60+60 秒和 12+12 秒通用对象树分析分别在约 4 分钟和约 2 分钟后主动终止，均未产生可使用结果；4+4 秒分析自身耗时约 65 秒，而模拟只耗时约 5.5 秒。B 档的通用分析约 20.9 秒，模拟约 4.0 秒。

因此：

- “对所有对象做深比较，再判断谁能休眠”是明确否决方案。
- 正式实现必须在规则执行时直接写 dirty bit、下一事件时间和唤醒原因。
- 当前证据支持把事件驱动的首版目标定为 A 约 12%～16%、B 约 27%～43% 的引擎下降；“5～50 倍”只能作为未来稳定离线岛的远期研究方向，不能写进 1.1.0 发布承诺。

## 6. 自动保存与浏览器证据

两份档各执行两次真实浏览器自动保存。两档均保持模拟 Worker active、`paused=false`，备份可读取，测试通过。

| 指标 | A：36.7 MB | B：10.0 MB |
| --- | ---: | ---: |
| 自动保存 1 | 4,715 ms | 2,029 ms |
| 自动保存 2 | 4,473 ms | 1,481 ms |
| 平均耗时 | 4,594 ms | 1,755 ms |
| 平均序列化阶段 | 1,225 ms | 621 ms |
| 平均主写入阶段 | 2,660 ms | 959 ms |
| 写入阶段占总时间 | 57.9% | 54.6% |
| 测试窗口最大 Long Task | 827 ms | 197 ms |

Long Task 来自 Vite 开发模式，只能作为开发诊断上界，不能冒充 production-preview 的发布数据。但它足以说明：“保存不会把游戏永久暂停”已经解决，“保存期间完全丝滑”尚未得到证明。

### 新发现的开发前 P0

36.7 MB 实时交互门禁连续两次在相同位置失败：进入工厂后等待 120 秒，`getLocalSaveRawCacheSize()` 仍为 1，期望为 0。测试因此未进入画布 6 秒帧采样。

已确认：

- 两次都是独立浏览器、独立端口和独立测试输出目录。
- 原件哈希未变，没有数据丢失证据。
- 失败表示至少一份完整原文仍被本地缓存逻辑持有；尚未证明它是生产模式回归。

开发前必须先在 dev 与 production-preview 分别复现并定位。未收口前，不能给当前 HEAD 的大档画布、浏览器堆或 RuntimeWorld 内存目标写“已通过”基线。

## 7. 百分比计划如何得出

以下不是拍脑袋相加，而是把实测阶段乘以假设改善幅度：

| 假设场景 | A 整周期下降 | B 整周期下降 |
| --- | ---: | ---: |
| 引擎降 20%，扫描降 70% | 24.7% | 27.6% |
| 引擎降 40%，扫描降 80% | 43.3% | 45.8% |
| 引擎降 60%，扫描降 85%，UI 应用降 50% | 62.2% | 63.7% |

所以 1.1.0 的合理分级是：

- 最低放行线：两档完整周期都下降至少 40%。
- 正式目标：两档下降至少 55%。
- 冲刺目标：接近 63%，只有实测达到才能写入发行说明。
- 不承诺 80%～90% 整局提升；现有两份真实档不支持这个数字。
