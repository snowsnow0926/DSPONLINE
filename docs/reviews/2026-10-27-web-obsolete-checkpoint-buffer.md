# 替换保存前释放旧检查点缓冲

状态：本地开发候选，未发布。接续 [共用后台验证](./2026-10-27-web-startup-shared-owner.md)，本轮优先检查额外内存的来源。

## 引用与诊断

`saveVerifiedPrimaryCheckpoint` 发现检查点与保存对象不同后，会清理全局 transfer 缓存，再异步保存新的冻结状态；但它的局部 `checkpoint` 变量仍可能让旧状态及整档二进制缓冲存活到函数返回。候选仅把这条已无法再使用的局部引用设为 `null`，不跳过普通 T0，不提前消费匹配的 transfer，也不改变任何存档字段或计算。

在真实大档进入产率复制、共用后台开始生成主档的同一个边界，分别暂停发送并请求一次诊断 GC：

| UI 上下文指标 | 前一轮基线 | 提前释放候选 |
| --- | ---: | ---: |
| `backingStorageSize` | 216,506,234 B | 9,664,647 B |
| `usedSize` | 1,360,514,724 B | 1,364,575,504 B |

二进制存储差约 206.84 MB。两次完整旅程都结束，存档完整性有效。这验证了引用的存活影响，**不是正常运行的峰值或速度提升**；强制 GC 的结果不能混入性能对照。

诊断开关为本地工具 `--startup-buffer-gc=1`，默认关闭；只记录数值，不记录存档内容。结果位于 `D:/GameDev/DSPidle2/artifacts/web-startup-buffer-20261027/gc-old.json` 和 `gc-drop.json`。后续将使用关闭该开关、关闭 profiler 的独立浏览器会话交替比较前一轮干净包与当前候选，并完成相应回归，才决定是否保留。

## 非强制回收的第一阶段结果

随后按旧→新→新→旧完成四次正常运行。旧进程峰值中位为 5.642 GB，范围 5.639～5.645 GB；释放局部引用后中位为 5.581 GB，范围 5.509～5.652 GB。范围重叠，第二次候选没有重复第一组的下降，不能宣布峰值稳定降低。进入等待中位 10.553→10.635 秒，最长间隔 436.65→419.80 ms；这轮没有足够强的整体性能收益结论。

局部引用修正保留，但还需处理更早的内存重叠。两个 T0 前置顺序均未取得足够收益，已恢复原顺序，见 [否决记录](./2026-10-27-web-startup-memory-order.md)。下一步独立验证 [保存后台的及时回收](./2026-10-27-web-startup-idle-retirement.md)。完整验证完成前不发布。
