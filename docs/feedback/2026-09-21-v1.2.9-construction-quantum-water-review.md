这证明该版本确实存在能造成玩家所述现象的代码路径。尚未取得该玩家的存档、目标建筑和量子需求槽配置，不能把合成复现中的触发配置直接认定为其现场根因。

## P1：缺货请求吞掉下载配额，水明明存在却不能交付

### 与本次反馈相符的复现

使用 `createPersistentSimulationRuntime()` / `advancePersistentSimulationRuntime()`，即 Web Worker 使用的常驻 JS 模拟入口；每次推进 1 秒，共 120 秒，经过 24 个五秒量子边界。没有开启挂机、离线或时间扭曲。

合成工厂：

- 一个建筑制造中心，满电，自动补足和量子直供均开启。
- 目标为 1 台地热发电站，其钛合金链需要合成硫酸，缺 16 水。
- 其他材料在中心所在行星托盘：钢材 23、钛块 8、精炼油 24、石头 32、处理器 4；相应科技已解锁。
- 共享量子仓库有 `water = 1000000`，没有氢。
- 一台已接入的量子塔，普通生成式 ID `entity_200`，每分钟下载额度 5,000，每个五秒边界整数额度 416。
- 该塔有一个远程“需求氢”的高优先级槽，中心直供的优先级固定为普通。

| 场景 | 结果 |
| --- | --- |
| 没有竞争需求槽 | 水变为 999,984，完成 1 台地热发电站 |
| 增加上述缺氢的高优先级需求 | 120 秒后水仍为 1,000,000，中心缓存没有水，完成数 0，状态“等待材料 / 缺水 16”，供电因子 1 |
| 仅把该槽远程模式从“需求”改为“仓储”后继续 | 不重置中心、不增加库存，自动取走 16 水并完成 1 台 |

恢复通过正式引擎命令 `setStationSlotMode()` 操作，不靠直接改内部索引或清空任务。

### 错误发生在哪里

- `src/game/engine.ts:6868` 附近把制造中心需求加入量子输出请求，优先级写死为 `1`；塔槽可以是 `2`。
- `src/game/quantumLogisticsNetwork.ts:541`：`allocateWithPriority(..., prepared.outputs, 0)` 先分全部下载额度，尚未核对每个物品可用库存。
- 同文件 `:544`–`:546` 才读取库存并截断当前物品可交付量。
- 同文件 `:556` 只记 `blockedInventory`，没有把缺货浪费的配额重新分给有货请求。

因此上述每个边界会把 416 额度先分给氢，再发现氢库存是零，实际下载零。水还有一百万也无法使用已经分掉的额度。条件不变时，相同分配会在后续边界重演。

这与“真实有货的高优先级产线优先使用带宽”不同：该案例没有完成任何高优先级交付，未实际使用的额度仍使其他请求无法交付。问题在全局量子分配器，影响范围可以超过制造中心，修复需要同时检查普通塔下载。

### 同优先级也有公平性缺口，但不能泛化现场结论

全局分配每次传入固定游标 `0`；按物品保存的 `routingCursors` 只在后续库存不足阶段起作用。如果全局带宽阶段已经把某个请求分成零，后面的按物品轮转无法救回它。

独立分配器复现：三个相同优先级端点 `a/b/c` 各请求 1、库存充足、总额度 1，连续九个边界都是 `a=1,b=0,c=0`。另一个缺货大请求和有货小请求的测试中，连续十二个边界两者实际交付都是零；移除缺货请求，有货请求立即交付。

完整引擎的同优先级永久等待例使用排序靠前的合成塔 ID `a-empty`。改成正常 `entity_200` 后，同一单中心小工厂能缓慢完成。因此不能声称所有普通优先级、正常 ID 的玩家必然永久卡死；这个反例已保留。**本次与正常生成 ID 完全匹配的缺水卡死复现，使用的是高优先级缺货槽。**

## P1：新任务看不到量子仓库的现成中间件

这是独立确认的直供规划缺口，会导致其他“库里有料却不拿”反馈，但不是本次“同名水已存在”的直接解释。

`src/game/engine.ts:6655` 新任务的虚拟库存只从中心私有缓存开始；随后 `:6658`–`:6671` 反复补全递归规划器报告的原料缺口，没有用共享仓库的真实现货选择可执行路线。`buildConstructionAutomationPlan()` 在 `:11655` 附近只合并行星托盘和传入的额外库存。

合成复现：量子仓库有恰好制造一座电弧熔炉所需的铁块 4、石材 2、电路板 4、磁线圈 2。满电运行 120 秒，四种现货全没取，完成数 0，仍提示缺铁矿石。同样的物料放在托盘，或已经在该中心直供缓存中，都能完成。

如果旧任务已经进入最终建筑步骤，则同样的量子仓库现货能够被请求并消费，因为有任务分支按既有步骤输入生成请求。这解释了为什么“有时能用半成品、有时又退回去要原矿”，不应把实现概括为所有时候只支持原矿。

修复方向：让需求规划能够识别可用量子现货，先区分已拥有的托盘/WIP/中心缓存与尚未交付的共享物资，再决定需要请求的材料和递归后缀。仍必须通过五秒分配和原子扣账，不可把仓库库存直接复制到每个中心，也不可绕过科技、配方及剩余库存约束。

## 多目标调度会放大一个缺料点

`src/game/engine.ts:11600` 的目标选择只寻找有目标缺口且已解锁的第一项，不检查材料可执行性。`runConstructionCenters()` 在 `:13018` 附近遇到 `plan.blocker` 直接 `break`，这次失败不会移动游标；无任务中心会继续选到同一项。

合成复现：电弧熔炉缺石头，后面的位面熔炉所需材料已经齐全。连续 120 秒两者都不生产；只取消电弧熔炉目标，位面熔炉即可完成。这个行为使一个缺水目标能够拖住其他目标，并使玩家感受到整套制造巨构停摆。

建议作为独立调度改进处理：在既有计算预算内尝试其他可执行目标；保留缺料目标、已投入 WIP 和恢复机会。不要通过取消全部任务、退库或重建存档来“疏通”。若希望保留严格顺序模式，需要在产品上明确表达，不能把隐式阻塞称为多目标公平调度。

## 当前界面不足以区分“缺货”和“有货但未配送”

- `src/game/engine.ts:11830` / `:11878` 附近的状态只检查托盘、当前任务 WIP 和本中心缓存；显示“缺水”并不表示它检查了全局仓库后认定没水。
- `src/components/ConstructionCenterWorkspace.tsx:215` 只显示直供开关是否开启；`:238` 显示“已启用”，没有显示该中心的实际请求量、分配量或最近成功收货时间。
- 分配器已有库存和带宽阻塞汇总，但正常在线调用没有将其转成按中心解释的状态。玩家会同时看到“直供已启用 / 缺水”和仓库大量水，却看不到为何未交付。
- 同文件 `:139` 附近把多个中心的专属缓存相加用于材料展示，而实际制造按每个中心自己的缓存扣料；多中心时“材料够”的展示与所有权不完全一致。

建议显示：真正缺货、等待五秒边界、没有下载带宽、等待共享下载额度、当前已请求/实际送达、中心可用量和量子库现货。界面信息应由模拟侧返回，避免界面再建立一套不同的需求算法。

## 本次排查确认的正常限制

1. **水可以量子直供**：合成对照在常驻 Web 模拟入口通过，没有发现针对流体或水 ID 的排除逻辑。
2. **每五个模拟秒结算一次**：一次不足五秒的观察不能证明卡死。本次卡死案例经过 24 个结算边界。
3. **启用仓库不等于拥有下载额度**：没有已接入量子塔时下载额度为零，即使仓库有水也会等。独立对照已复现；本次主要缺陷复现则明确有 5,000/min 额度。
4. **中心仍需供电**：主要复现供电因子为 1，不依赖低电或断电。
5. **私有直供缓存不经过行星托盘容量**：没有证据支持通过提高托盘容量修复上述问题。

## 为什么既有测试没有发现

本轮现有四个相关测试文件共 **35 通过 / 0 失败 / 0 跳过**。全部通过并不排除上述缺陷：

- `quantumLogisticsNetwork.test.ts` 的制造直供工厂主要提供铁矿石、铜矿石、石头，量子塔没有竞争下载槽，验证了有货、无竞争的顺畅路径。
- 名为公平轮转的测试在 `:228` 附近主要验证输入排列不影响一次分配，没有设置跨物品全局带宽竞争，也没有检查多个连续边界中零份额端点是否得到服务。
- `constructionReferencePath.test.ts` 直接把材料放入中心缓存，跳过了“发现需求 → 争用带宽 → 从共享仓库交付”的路径。
- 缺料恢复测试主要向行星托盘补原料，没有验证量子仓库已有同名材料却没有交付的场景。

这反映出回归覆盖集中于批量吞吐、守恒、容量和崩溃保护，缺少多层库存与共享带宽竞争中的持续前进验证。

## 修复顺序及验收要求

第一步优先修复下载分配器：先计算仓库能兑现的需求，再进行跨物品全局带宽分配，或在有界算法中将无法交付的额度重新分配；优先级规则只应作用于可兑现的请求。不能简单提升所有制造中心的优先级，否则会把问题转移到其他产线。

第二步处理全局余数轮转，保证同优先级的持续可兑现需求不会因键名或微小整数份额长期为零。若新增持久游标，需同步规范化、旧档默认值和保存恢复测试；不要把暂态诊断字段混入存档契约。

第三步改进中心的现货规划及缺料目标调度；第四步补上配送状态说明。前两步适合先形成一个针对缺水反馈的最小修复，后两步需独立回归，避免一次大改递归规划和所有权。

| 验收场景 | 必须满足 |
| --- | --- |
| 百万水 + 缺货高优先级氢槽 | 水需求可获实际剩余额度，自动完成，不要求清空任务 |
| 高优先级槽部分有货 | 仅实际可交付数量消耗额度，余量继续供给其他请求 |
| 多中心、多种物品、紧张带宽 | 分配确定、总量不超限、同级可执行请求有持续前进保证 |
| 当前目标缺原料、后续目标齐料 | 若采用跳过策略，保留前者并有界推进后者，补货后自动恢复 |
| 仓库只存现成中间件 | 开关开启时能按库存规划并交付；关闭时保持原规则 |
| 旧 job、部分 WIP、取消目标、拆中心 | 原料、半成品、在途和中心缓存总量守恒，不重复退款或复制库存 |
| 保存重载、不同请求切片 | 库存、进度和公平性结果一致，旧 v47 正常加载 |
| 普通塔、既有纯挂机/离线路径 | 共享分配器改动不得破坏旧物资账本；需要相关专项回归 |

## 可用的临时诊断办法

检查量子仓库页面的“下载额度”、最近结算时间和水的最近下载量。若有下载额度、结算时间持续推进、水很多却连续多个边界下载为零，重点检查设置为高优先级且长期缺货的远程需求槽。

对确认没有现货可供的那个槽，可暂时改成远程“仓储”观察制造中心是否恢复。本次合成场景已验证这一路径自动恢复，不需要拆中心、反复开关直供或清档。这是配置对照，不是对所有玩家的通用修复；不要随意停掉有真实供货的关键产线。

若现场没有此类槽，需要记录目标建筑、中心 ID/供电、`water` 的请求量和实际交付量、全局下载额度、其他可兑现/不可兑现请求以及五秒边界前后状态。仅凭“库里有水”的汇总还不能区分零带宽、优先级占用、全局份额归零或其他任务状态。
