## 这轮具体做了什么

存档保存会反复检查完整文本，确认读写过程中内容没有变化。我把常见的连续英文字符和数字改为每轮处理四个，仍按原顺序计算；中文、emoji 和特殊字符的处理规则保持原样。没有删掉校验、备份或快照。

完整原档的新旧校验结果一致。单个校验函数的中位耗时约减少 28.4%，但一个新样本更慢，密集 Unicode 小样本也有反向变化；**真正完整保存只快约 2.2%**，应以这个较小的流程收益理解当前结果。

云端还有一项 Rust 检查要求至少两条线程真的参与解析，但短任务有时被一条线程提前做完。我为这类测试补上已有的有界同步前提，保留原实际参与断言和时限。这个改动用于让正确性检查可靠，不是新的玩家性能收益，也没有修改生产线程调度。

旧的 `37630d05` 包通过过取消保档及取消后两次重开；不能把这份旧结果算到新包头上。本轮新校验代码也还需要新包验证。

原始存档保持不变。新包两次启动均没有显示、聚焦或弹系统对话框，两次正常关闭。随后六次无头浏览器保存全部核对了完整主档、原文备份与快照状态，原档未改。详细证据见[本轮技术记录](./reviews/rust-rp1-save-checksum-2026-09-09.md)。

## 网页和安卓能否受益

Windows 开发包已接受限 Rust 短离线计算，当前采用范围仍为 **1–30 秒**。网页和安卓还没有接入本批 Rust 核心；保存校验、电力统计等共享 JS 优化可以随它们后续发布生效。本轮尚未上线任何客户端，Rust 长离线自动采用和实时接管保持关闭。

## 距离做完还差多少

**现在处于 RP1：把 Rust 离线计算变成可靠的实际收益。底层已有大量实现，公开大工厂也已有可用结果，但超大终局档和完整回归还没有收口。** 目前还不是全面 Rust 接管游戏的阶段，也没有可信的总完成百分比。

当前 RP1 收尾还有三组关键工作：

1. **终局档完整闭环**：成功结算后进入可操作工厂，核对完整持久状态、正常退出与两次重开，再做同档新旧完整等待对照。现在卡在原 90 秒进入工厂门槛。
2. **稳定性与回归**：收齐本批 Windows 云端结果，逐类处理完整浏览器的 11 项失败，保留取消、失败重试、时间预算和原档不变的验证；历史堆异常继续按已隔离证据管理。
3. **冻结可交付候选**：把最终源码、Host、桌面包、性能证据和回退材料绑定，复验真实入口。正式发布仍是后续独立任务。

以一个熟悉项目的人全职处理计算，**这三组收尾暂按约 5–10 人日预留，置信度中低**：终局优化与闭环约 2–4 人日，回归与故障验证约 2–4 人日，冻结交付约 1–2 人日。这是依据当前缺口的新排期估算，不是实测工期，也不是承诺若干小时后上线；终局结果与新云端回归出来后应重估。它不包含放开长离线、实时接管或跨端 Rust。
