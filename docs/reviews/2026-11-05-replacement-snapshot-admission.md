## 已复现的问题

在一次性浏览器中建立铁矿 42、12 份蓝图、科技 electromagnetism、自动保存 0 的原档。导出原档，再构造铁矿 99、蓝图 0 的外部候选。只覆盖该浏览器的 StorageEstimate，让新恢复快照因可用空间判断返回失败，而较小的主档替换仍可写；不填充硬盘，不改变操作系统或其他项目。

冻结 `bf6df340bedc` 上两条独立公开流程确认：

- `replacement-snapshot-red-53`：救援创建回滚快照失败后仍替换主档，提示“存档救援完成，原始异常文件与当前工厂回滚快照均已保留”；快照实际 0，刷新后铁矿 99。
- `replacement-cloud-red-57`：模拟账户的云恢复同样在快照 0 时替换，刷新并导出的主档铁矿 99。接口全部被本地模拟拦截，没有真实登录、上传或生产 API 操作。

普通文件导入已有快照失败检查，救援与云恢复漏检了 `saveGameSnapshotVerified` 的 null 返回值。两处现在只在快照验证成功后调用主档保存和替换；失败保留待处理候选，给出中英文错误和重试提示。原生权威保护仍在入口优先执行。原始异常文件的备份下载仍在救援前完成，失败不伪称回滚快照成功。

通用的 App 私有不可用反馈从临时存储专用名称改为 `reportUnavailableLocalSave`，供新失败原因复用；主存档/槽位/手动快照原有反馈保持。没有改公共存储 API、fencing、序列化、保留策略、GameState 或云协议。
