## 给小白看的结论

以前保存一次大工厂时，程序会把约 77 MB 的完整状态重新拼一遍，同时还要在内存里保留检查点、JSON 字符串和写入缓冲区。保存和模拟又可能同时进行，所以峰值内存会突然变大，浏览器容易卡死或崩溃。

1.1.8 把这件事拆成五道保护，并把自动暂停交给玩家选择：

1. **先看内存再做事（P0）**：大工厂使用 1 秒小切片；模拟积压超过 8 秒先停止继续塞新任务，超过 24 秒、堆内存达到约 90% 或发生分配失败时，自动暂停在最近一个已确认检查点。暂停会清掉未确认的追赶队列，不会把半成品状态当成存档。
2. **保存和模拟互斥（P0）**：保存检查点期间不再继续产生新的模拟积压；自动保存重复触发时合并成一次。
3. **只写变化区块（P1）**：第一次大存档仍写完整“种子”；之后把基础字段、建筑区块、传送带区块分开，只写发生变化的区块。手动保存、页面离开和纯挂机停止时会写回完整 v2 存档并清理旧 sidecar。
4. **线路只算活跃部分（P1）**：没有货物、生产信号或历史流量的线路先放入休眠队列；有新产出时自动唤醒。这样不会每个模拟秒都把全部线路当成有货线路检查。
5. **带校验的紧凑 sidecar（P2）**：每个区块有字节数和校验码，清单还有根校验码。损坏、缺块或和主存档不匹配时，程序放弃 sidecar，继续使用旧的完整 v47 主存档。

### 内存保护设置（设备级）

- 默认：开启，使用浏览器 JS 堆上限的 90% 作为自动暂停水位。
- 固定水位：512 MiB、768 MiB、1 GiB、1.5 GiB、2 GiB、3 GiB、4 GiB。固定水位只会更早触发保护；浏览器仍保留 90% 的硬上限。
- 关闭：只关闭“JS 堆水位”这一触发条件，不关闭模拟积压超过 24 秒、Worker 连续失败或内存分配失败的硬暂停。
- 存储范围：写入本机 `localStorage`，不进入 GameState、v47 存档正文、云上传、云合并或确定性哈希；换设备不会同步。
- 限制：浏览器没有 `performance.memory` 时无法显示可靠堆数值，程序仍使用队列、Worker 和分配失败保护；关闭后玩家自行承担更高的浏览器崩溃风险。

本轮还修正了一个保存状态边界：内存闸门拒绝自动保存或纯挂机终态保存时，现在会记录 `persistence-phase: failed`、结束对应 transition、保留最近检查点并给出可重试状态，不再让界面永久停在“保存中”。

## 实测对比

测试存档包含 `80,674` 个建筑实体、`155,746` 条传送带、`36,754` 个空间站实体、20 个星球。

| 项目 | 旧的完整保存方式 | 1.1.8 优化路径 | 结果 |
| --- | ---: | ---: | --- |
| 首次种子保存 | 约 76.898 MB | 约 76.898 MB | 首次必须建立可回退的完整基线 |
| 人为只改 1 个基础区块 | 约 76.898 MB | `388,446` 字节 | 写入量减少约 **99.5%** |
| 同一 Node 基准的增量峰值 RSS | `1,582,305,280` 字节 | `1,215,332,352` 字节 | 峰值降低约 **23.2%** |
| 真实 Chromium 自动保存第 1 次 | `76,898,154` 字节 | `76,898,154` 字节 | 作为种子 |
| 真实 Chromium 自动保存第 2 次 | 仍需完整状态 | `9,080,989` 字节 | 本次运行少写约 **88.2%**；若没有任何区块变化则可为 0 |
| 真实 Chromium 纯挂机 60 秒（最终复测） | 1.1.7 旧长时基线持续上升 | 进程私有峰值 `2.32 GiB`，无 pageerror，最终安全暂停 | 1.1.8 保护生效 |
| 真实 Chromium 建造/拉线/蓝图 + 自动保存（最终复测） | — | 进程私有峰值 `4.57 GiB`，3 轮编辑 + 3 次保存均完成，无 pageerror | 保存完成状态可观察、未悬挂 |
| 启动 JavaScript gzip | 1.1.7 历史基线约 `101,993` 字节 | `85,724` 字节 | 约少 **16.0%**；本次把本地存档初始化移到游戏路由后 |

内存基准使用 `NODE_OPTIONS=--expose-gc` 在相同 Node 进程中测量，`afterIncremental` 的堆在强制 GC 后回到约 509 MB；这说明增量路径没有把上一轮完整 77 MB 的临时区块表长期留在内存里。它是可重复的工程基准，不等同于每台浏览器的绝对峰值。

## 正确性与物流结果

- 真实 v47 存档 1 秒精确模拟：`hash=864af4fc`、`gameplayHash=4b08545d`；切片结果哈希一致。
- 资源守恒检查：`invalidAmounts=0`、`routeCargo=0`、`finiteVeinRemaining=0`；没有出现负数、NaN 或非法大整数。
- 该真实存档的所有线路本来都处于活跃状态，因此本次精确基准的 `beltStableRoutesSkipped=0` 是合理结果，不代表休眠队列失效。休眠队列的唤醒行为由专门单测覆盖。
- 现有 indexed-logistics 基准的哈希保持一致，10/50/100/128/300/500 站规模的中位耗时改善约 61%–85%；这组数字是整个索引物流基准的支撑数据，不把全部收益归因于本次休眠线路改动。

## 兼容性与限制

- 对外仍是 `formatVersion=2`、`stateVersion=47`，没有强制升级到不可读的新 v48。1.1.7 读取到的是最后一次完整主存档，并会忽略 `dsp-idle-network.internal.v1.*` sidecar；因此降级安全，但可能落后于尚未合并的最近一次自动保存。
- 1.1.8 只有在 sidecar 清单的主存档校验码完全匹配时才覆盖读取结果。任何缺块、重复 ID、字节数/校验码错误都会回退到完整主存档。
- sidecar 需要 IndexedDB。浏览器只提供 localStorage 或内存后端时，自动回退到经过验证的完整保存，不牺牲可恢复性。
- 第一次大存档仍需建立 157 个区块；之后虽然只写变化区块，但当前实现仍会投影并扫描/哈希全部区块来判断变化，CPU 方面还可以继续做“脏区块索引”。
- 浏览器没有 `performance.memory` 时，内存数值按“未知”处理，仍使用队列上限、Worker 慢片段和保存互斥保护；不会因为缺少浏览器 API 直接误判崩溃。

### 全量 E2E 失败分类

本轮完整 Chromium 是 456 个用例：383 通过、34 跳过、39 个 unexpected。对照 `D:\GameDev\DSPidle2-v118-baseline`（基线 `90bd4d5`）复跑后，保存 revision 计数、保存预览冲突和若干离线/存储超时均可在未改动代码的基线上复现；版本公告、教程版本和 `v139` 候选版本断言已更新到 1.1.8，聚焦回归通过。剩余失败主要是历史 E2E 在同一浏览器进程串行运行时的跨测试状态/超时，以及已有的纯挂机停止、离线结算、Canvas 性能阈值和本地存储协调基线问题。它们已单独记录，不能标记为 1.1.8 内存设置功能通过或失败；Release Agent 合并前应在其干净候选环境按发布矩阵重跑并决定是否继续保留这些历史测试。
