# 1.1.8 真实存档长时间内存压力测试报告

测试日期：2026-08-25
测试目标：用玩家提供的真实工厂存档，对比 1.1.7 候选代码与 1.1.8 内存优化代码在挂机、建造、拉线、蓝图和自动保存时的内存峰值与安全行为。

## 结论先看

1.1.8 已经解决了“纯挂机持续上涨到 5 GB 仍不收手”的主要风险：180 秒纯挂机时，默认保护开启的 1.1.8 在约 21 秒主动安全暂停，之后内存没有继续线性增长；同口径 1.1.7 没有暂停，最终达到约 5.60 GB 私有内存（按所有隔离 Chrome 进程合计的峰值计算）。现在关闭保护时会进入明确标注的“不自动回档”高级模式：积压和堆水位不再把状态切回旧检查点，但浏览器可能卡死或崩溃。

但 1.1.8 还不是“任何操作都不会接近 5 GB”：建造/拉线和保存会制造大型状态副本，组合压力峰值仍达到约 5.12 GB。1.1.8 比 1.1.7 低约 14.7%，并且多完成了一轮操作+保存。本轮已补齐保存被内存闸门拒绝后的状态收尾，并用最终 60 秒复测确认保存结果会进入明确的 complete/failed 终态，不再悬挂。

- 存档：dsp-idle-save-2026-08-24 (1).json
- 存档大小：76,898,141 字节；SHA-256：AB869C2B52D5F89E1FCBD8BF…
- 规模：80,674 个实体、155,746 条线路、约 36,754 个物流站；v47 状态 / v2 存档封套。
- 1.1.8 工作树：D:\GameDev\DSPidle2-v118-memory-optimization；本轮最终候选提交以交接末尾的 Git handoff 为准。
- 1.1.7 对照工作树：D:\GameDev\DSPidle2-v117-development，提交 2dca5770b1a5139231ebace6419103102ecc4807。只启动本地只读服务，没有修改或发布该工作树。
- 相同机器、相同 Chrome 147.0.7727.138、Node v24.14.0；每个测试使用独立临时浏览器目录，结束后删除。
- 存档通过真实导入界面加载；建造/拉线/蓝图操作在从真实存档迁移出的隔离状态副本上执行，原始存档没有被写回。

本文主表使用“隔离 Chrome 进程私有内存合计峰值”：每次采样把浏览器、renderer、GPU 和 utility 进程的私有字节相加，再取整个测试期间的最高值。它比只看 JS 堆或只看 renderer 更接近系统实际承诺的内存；GiB 是二进制单位，括号内给出十进制 GB 便于和任务管理器比较。

### 1.1.8 设置/保存终态最终复测（代码冻结后）

同一真实存档、同一 headless Chrome 隔离目录，在修正保存失败终态并把压力保护设置接入运行时后再次执行：

| 场景 | 配置/结果 |
|---|---|
| 纯挂机 60 秒 | 进程私有内存合计峰值 `2.32 GiB`（CDP JS heap `826.53 MiB`、页面 `performance.memory` 峰值 `1000.87 MiB`），无 pageerror，最终 `data-simulation-paused=true`。 |
| 建造/拉线/蓝图 + 自动保存 | 3 轮放置/拆除/重连/蓝图和 3 次自动保存均完成；进程私有内存合计峰值 `4.57 GiB`，无 pageerror，最终安全暂停。 |
| 自动保存终态 | 三次 `triggered=true, completed=true`，没有 120 秒等待超时；存档失败时会记录 `persistence-phase: failed` 并保留恢复边界。 |

这组 60 秒结果用于确认本轮代码改动的行为，不替代上方 1.1.7/1.1.8 同口径 180 秒历史对照；绝对峰值会受开发服务器和机器状态影响。

补充：上表的“建造”不是只点按钮计数，而是每轮真实调用普通 storage_mk1 放置 10 次、拆除 10 次；“拉线”是拆除并重连 10 条已有线路；另创建并删除 1 个蓝图。60 秒建造+拉线场景共执行 30 次放置、30 次拆除、30 次线路重连和 3 次蓝图创建/删除。1.1.7 在组合场景因单轮耗时更长，只完成了 2 轮和 2 次保存。

## 180 秒纯挂机的关键证据

- 1.1.8：约 21 秒第一次进入安全暂停；之后继续采样到 180 秒，私有内存峰值 2.25 GiB，未出现页面错误或崩溃。
- 1.1.7：没有安全暂停；内存随时间继续上升，180 秒峰值 5.21 GiB，最终 Worker 仍显示 active。
- 这说明 1.1.8 的安全闸门确实截断了“持续运行导致的线性增长”。它是防崩溃措施，不代表暂停前的高负载已经完全消失。

## 保存压力的关键证据

旧的 1.1.8 180 秒保存记录中，第 7 次在内存闸门已暂停后曾没有产生可观察到的 complete/failed 收尾，测试等待 120 秒超时。该问题已修复：内存保护拒绝保存现在明确结束 autosave/pure-idle transition、清理进行中进度并保留可重试失败结果；最终 60 秒组合复测的 3/3 自动保存均在等待窗口内完成。

1.1.7 同口径只完成 4/5 次保存，第 5 次也在等待超时；完整保存路径更慢、峰值更高。1.1.8 的分块增量保存已经降低了大部分重复写入和暂存压力，但“保存前检查 + 序列化峰值”的瞬时成本仍然存在。

## 对玩家体验的解释

- 只挂机：默认保护开启时，1.1.8 会先让工厂运行一段时间，然后在内存危险前自动暂停。暂停是保护动作，不是产量结算错误；恢复前应让浏览器内存回落。关闭保护后不会因堆水位或积压回档，但风险转为浏览器卡死/崩溃。
- 建造/拉线：每次编辑仍要复制很大的 GameState，短时间连续编辑比纯挂机更容易冲高内存。1.1.8 目前主要保护模拟和保存，尚未把所有编辑操作改成共享结构或一次性批处理。
- 保存：分块保存减少了“每次都写完整 77 MB”的后续写入量，但第一次完整检查点和编辑期间的临时对象仍可能把峰值推高。不要把 JS 堆峰值、renderer 工作集和系统总私有内存混为同一个数。

## 后续建议

1. **继续做编辑增量化（P1）**：建造/拆除/拉线批量操作应复用一次 draft 或结构共享，避免每条线路都复制 80k 实体和 155k 线路；编辑期间减少全量 React/Canvas 重建。
2. **默认保留 1.1.8 安全暂停（P0）**：默认设置仍应保留堆内存和积压熔断；同时保留已经实现的“不自动回档”高级开关，并在 UI 明确警告其崩溃/丢失最近未保存进度风险。
3. **发布前观察**：Release Agent 在干净候选环境重复 180 秒纯挂机和 60 秒组合场景，并在低内存实体机上做一次非 headless 验证；线上灰度记录自动暂停次数、sidecar 回退次数和 changed bytes。
