# 游戏整体性能复盘与下一阶段优先级

状态：方案已获用户批准，2026-10-27 建立的持续性能开发 goal 当前运行中，不自行暂停。界面查询局部优化 `4ea4aab3aa8e` 已验证；随后 `b77a420df80f` 的正式退出帧降至约 163 ms（少 42.92%），完整回归通过，见 [恢复优化记录](./2026-10-27-web-idle-reveal-styles.md)。继续处理约 0.43 秒进入帧，诊断优先指向供电查询索引。下文旧数字仍为复盘时 `9f0d9f7072ae` 与正式 1.3.3 `a0fd77efc399` 的证据，目标值不代表已经实现。存档、材料规则及自动备份停用设置保持；当前执行开发与测试，未发布。

## 总体判断

当前主要问题分成三种，不能用一个“加速倍率”概括：

1. **平时持续计算偏重**：普通模拟需要处理大量运输线、物流与电力；大档每个推进周期都有成本。
2. **切换时要搬运和恢复大量数据**：开始/停止挂机、加载、保存和离线返回会同时涉及检查点、序列化、解码、数据库与界面恢复。
3. **低内存与长时场景的资格不足**：当前桌面大档能完成流程，仍有约 5 GB 峰值；手机、低内存设备、长离线和长期挂机需要专门验证。

建议先做“大档数据通路”和“普通模拟运输线”两条主线。巨构制造仍可继续优化，但目前不应把全部精力继续放在它一个模块上。

## 已有证据与边界

### 普通模拟：运输线是当前样本最大的计算项

从 `artifacts/web-replication-stages-20261027/normal-new.json` 读取同一大档固定推进 30 个模拟秒的阶段计时：

| 指标 | 本机该样本记录 |
| --- | ---: |
| 完整推进调用累计时间 | 18.71 秒 |
| 传送带阶段 | 7.93 秒，约占调用累计时间 42.4% |
| 其中：线路扫描 | 6.18 秒，属于传送带阶段子项 |
| 物流阶段 | 2.75 秒 |
| 电力阶段 | 2.43 秒 |
| 普通生产阶段 | 1.45 秒 |
| 量子阶段 | 1.16 秒，可能与物流计时嵌套，不和其他项直接相加 |
| 制造阶段 | 0.58 秒 |
| 历史统计 / 戴森阶段 | 0.43 / 0.33 秒 |

这是一次阶段诊断，不是所有存档的占比，也不是帧率。计时字段有嵌套，不能把表中所有值加总。该样本有 233,300 条运输线，30 个模拟秒累计记录 13,998,000 次线路检查，稳定线路跳过计数为 0。

代码已经有持久索引、容量/源库存账本和活跃线路队列。因此下一步是核对现有队列在该档没有跳过线路的原因，优化仍需扫描的动态判断和数据布局，扩大可以证明安全的跳过范围；不能直接假设“空线全都不用算”。

### 切换与保存：计算提速之后，数据链仍占明显时间

当前直接与正式 1.3.3 的对照中，开始挂机仍约 10.82 秒，停止并保存约 12.88 秒，进程峰值中位约 5.03 GB；退出恢复画面的最长间隔约 0.33 秒，高于对照的约 0.27 秒。

当前两次停止记录分段：结算并生成终态约 4.38～4.44 秒，规范化状态到主档交接约 4.07～4.16 秒，主档提交到画布恢复约 4.35 秒。最后一段包含验证、数据库和恢复工作，不能全部称为磁盘写入耗时。

已有工作包含分批交接、后台共用、差量投影、空闲后台回收、范围扫描校验。持久化校验已经使用 `canonicalSaveEnvelopeInspection` 扫描器，没有把整个状态再次 `JSON.parse`；后续须进一步分解这些现有步骤，不能重复建议已完成的优化，也不能删除独立读回或校验。

### 仍缺少的证据

- 正常玩 30～120 分钟、反复切换工作区和挂机后的内存曲线。
- 真实低内存设备、手机浏览器及大档长期运行。
- 大档守恒模式、1 小时 / 24 小时 / 多日离线的完整计算与恢复表现。
- 当前服务器在真实并发和大云档上传时的新负载记录。本轮未访问服务器，不把客户端耗时归因于云端。

## 建议优先级

| 顺序 | 方向 | 要做的具体工作 | 首要验收 |
| --- | --- | --- | --- |
| 1，最高 | 大档数据通路、退出恢复与内存 | 先修复退出画面 0.33 秒短停顿；分清解码、哈希、复制、数据库等待和界面派生的耗时；复用既有受控后台及证明，减少仍同时存活的完整状态和字符串，按真正可见内容恢复界面 | 完整存档与失败恢复不变；退出不再退步；同档切换等待和峰值有可重复下降 |
| 2，高 | 普通模拟中的传送带 | 围绕 7.93 秒阶段和 1,399.8 万次检查展开；复用既有活跃队列，分析跳过为零的原因；减少重复分类、动态属性读取和临时对象，试验紧凑路由列；有条件地复用两次结算之间不变的工作 | 同序线路、多输入输出、公平分配、堵塞恢复与在途物资完全一致；完整推进总时间下降 |
| 3，高 | 物流、量子和电力的增量计算 | 在运输线改动稳定后，按真正变化的库存、站点、路由、电网更新；缩小全局汇总范围；复用稳定目录，减少相同供应/需求的重复扫描 | 高级配方优先、共享带宽竞争、燃料、储能和容量边界不变 |
| 4，高风险专项 | 离线、守恒模式和长期挂机 | 用相同底层热点优化逐步结算；保留明确的周期、断料、燃料、矿脉、研究和终局事件边界；补长时进度、取消、恢复及低内存资格 | 同一初态和时间得到同一完整结果；不重复结算、不凭空补材料；长任务可中断且原档安全 |
| 5，中 | 画布、工作区和统计界面 | 复查视口外计算、历史统计派生和多次重复汇总；使用已有差量模型，减少无关变化触发的全局更新；验证拖动、缩放、切星球、打开科技/统计页 | 操作延迟与长帧下降；显示数值和选中实体及时更新，不显示旧结果 |
| 6，按证据推进 | Rust/WASM、小包加载和云端链路 | Rust 优先用于前述已定位热点的紧凑批量计算，端到端包含转换与回写；云端另做只读诊断和隔离压测，首屏资源按真实瀑布图处理 | 先证明收益，再接入；网页版效果独立验证，不套用 Windows 内核数据 |

### 关键安全边界

- 运输线即使暂时无货，仍可能有在途、信用进度、流量衰减或同一步中新产物；跳过规则必须覆盖这些事件。
- 工厂暂停生产不等于燃料、储能、矿脉、物流返航和离线时钟都能冻结。
- UI 可减少派生与重绘频率，模拟时间、库存和玩家输入的处理仍须准确。
- 保存、离线、时间扭曲共享优化基础，但每条入口均要独立证明取消、接管、重试和完整结果一致。

## Rust/WASM 的位置

已有 Rust 规划器完成过 285 个浏览器差分场景，但现有 JSON 接口端到端慢于 JS，不能直接替换。它应是前述热点中的一个实现选项，而不是先重写全部游戏：固定目录与编号、成批输入、紧凑数组、只返回必要变化；把初始化、转换、内存和回写都纳入测量。校验或扫描部分同样先测当前真实耗时，再决定是否值得迁移。

## 执行顺序与验收目标

建议下一轮先集中做顺序 1：退出恢复短停顿和保存数据链。之后进入顺序 2，解决普通模拟最大计算项；顺序 3 随其索引和数据结构复用推进。顺序 4 先建立长时基线，再逐步接入已通过的改动；UI 和云端问题按独立证据插入。

以下是候选验收目标，不是已经取得的收益或工期承诺：

- 第一阶段争取把该大档退出恢复的最长间隔从约 330 ms 降到 150 ms 以内，并消除偶发明显退步。
- 大档加载/保存项目应在实际网页上体现稳定的等待或峰值下降，不能仅以某个函数变快验收。
- 传送带阶段若减半，按本次 42.4% 占比估算，理论上约能减少 21% 的普通模拟总计算；实际目标与保留决定必须由完整引擎和网页复测确认。
- 每轮保留相同存档、设置和目标时长的旧/新交替对照，报告中位数与范围；强制 GC 和 CPU 插桩只用于定位。
- 引擎和存档改动继续要求完整结果比对、适当故障测试及完整回归。已出现副作用或没有实际收益的方案撤回。
- 不改变 GameState v47、现有存档兼容、材料守恒和自动备份停用设置；发布仍需独立发布指令。
