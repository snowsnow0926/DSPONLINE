# Web 存档校验：既有 Rust 与 JS 的完整成本验证

结论：本轮测试的 Rust/WASM FNV 接口和两种 JS 八字节展开原型均不接入游戏。现有 JS 在该完整字节校验边界更合适。游戏运行、默认单元、native 和包版本仍与已接受 `3b7f35061a69` 相同；原有优化保留，整体性能目标 active，未发布，未访问生产或修改存档/备份设置。

## 实际测量

只读终局夹具按原持久化投影和 envelope v2 生成 **110,789,823 B** 原始载荷；完整 SHA-256 为 `22cbbcd7aae757d67b376028c15bf21f84596df4c418253cba9706c775589962`，字节 FNV 为 `339f5052`。不是对约 105 MB 原档的扩大保存，也不是把展开的 prepared 文件当上传格式。

Rust 直接调用未修改的 `dsp_native_core::canonical::fnv1a_utf8`。独立适配缓冲区保持原制造实验的 8 MiB 上限不变；`--locked` 的 wasm32 release 构建通过，5.77 秒完成。冻结 `kernel.wasm` **756,290 B**，SHA-256 `95191448069f776c6aba199a91d27a24eb4562f51e8df13a7aaa343eb90e9340`。编译缓存中原有两份二进制先独立备份并核对 SHA，没有覆盖唯一旧工件。

Chrome 147.0.7727.138，先三次全新浏览器，再三次加入输入视图控制的全新浏览器。各实现每次交替测两次；计时包含 WASM 分配、完整输入复制、函数调用、输出编码与结果读回，首次另计本地加载/编译/实例化。每次均通过 21 个空值、Unicode、全字节、偏移/尾长向量，以及超限拒绝后再次调用；完整输入 SHA 前后一致。准备存档和 SHA 在计时外，无强制 GC。

| 局部调用中位耗时 | 首三次浏览器 | 对齐生产输入视图后的三次 |
| --- | ---: | ---: |
| 生产 JS 单循环 | **82.60 ms** | **83.00 ms** |
| JS 八字节展开，直接视图参数 | 159.60 ms（+93.22%） | 157.20 ms（+89.40%） |
| JS 八字节展开，生产同样的固定长度视图构造 | 未测 | 158.25 ms（+90.66%） |

| Rust/WASM，首次含本地加载 | 118.60 ms | 132.60 ms |

两批每个实例都保留 **112,001,024 B 线性内存**；这是新接口需要的 WASM 内存，不是系统/进程工作集。首次加载是 loopback，不能当成香港公网下载时间。第二批排除“展开原型少了生产视图构造”这一实现差异后，结果仍未改善；不能只挑 Rust 核心时间或某个单次样本。

## 范围与后续

这是原始 UTF-8 字节 FNV 的局部完整调用成本，和 envelope 的 UTF-16 状态校验不同。没有验证或宣称整个游戏、其它 Rust 模块、数据库、离线、守恒模式、手机或低内存资格；没有换算法、删检查点、跳过独立校验或读回。

证据在本机忽略目录 `artifacts/web-payload-checksum-20261028/`，包含锁定构建日志、旧缓存保全、不可变 WASM、六次原始结果和 `cost-comparison.json`。源码/工件/原始结果摘要及两批来源均保留；未公开存档正文。

进一步检查转向更重的结构扫描。字符跨过、token 定位与数组栈复用均只留在实验，尚无可接受整页收益；当前继续对照“局部哈希累加器”与旧扫描器，保持所有字符、原顺序和完整 UTF-16 校验。必须先核对公开有效/异常用例和大档完整返回值，再决定是否形成运行候选、执行完整回归与冻结网页验收。
