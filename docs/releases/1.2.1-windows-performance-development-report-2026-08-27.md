## 1. 结论

1.2.1 完成了第二、三层现有开发候选的下一轮大型存档热路径优化，但**没有宣称《Windows 高性能架构三层开发计划书》的后两层已经全部完成**。

- 第二层的受限原生文件服务、内容寻址区块、WAL、双 superblock、原子 generation、v47 兼容出口和失败关闭恢复已经存在；本版进一步减少健康最新 generation 的重复恢复校验，并让相同 Worker 权威 revision 的重复保存复用已验证集合页。
- 第三层的 Rust 独立状态、主要精确模拟域、命令、投影、哈希和影子差分已经存在；本版进一步减少冷启动重复解析、规范摘要重复扫描和事务候选的整厂字符串复制。
- JavaScript 仍是唯一玩家可见权威，`authorityEligible=false`。完整原生纯挂机/离线时间扭曲、`CORE-390` 权威切换、三档硬件、24 小时 Gate C、正式签名 Beta 和观察期均未完成。

因此，1.2.1 可以作为“Windows 原生影子基础与大型存档热路径优化”候选，不能作为“三层全部完成”的稳定版证据。

## 2. 本版实现

### 2.1 原生存档恢复

- 原生 Host 在一次 generation 身份校验后批量读取核心所需记录，不再为每个逻辑记录重复执行 recover/WAL 恢复。
- 恢复先检查便宜的 superblock/manifest 身份，再按 revision、generation 从新到旧验证 payload；健康最新代际通过后立即停止，不再无条件解压两个保留代际。
- manifest 的 base chunk 明确拒绝内嵌 `entities` 或 `belts`，防止绕过有界集合布局。
- 自定义输出目录发生 Windows 文件锁时，打包回退现在从同一个已解析输出目录寻找临时 Electron 分发。

### 2.2 原生核心冷启动、摘要与事务内存

- checkpoint 集合页使用 serde raw JSON record 读取，解析后的实体/线路值同时供索引和线路路由准备使用，避免“读页一次、建索引再解析、建路由再解析”。
- 原始实体和线路记录改为共享不可变 `Arc<str>`；事务候选只为实际改变的记录分配新字符串，未变化的 80,000+ 实体和 155,000+ 线路共享原记录。
- 暂停等只改顶层字段的命令不再重建全部实体/线路索引。
- 规范根哈希、组件哈希、字段哈希和领域摘要合并为一次实体/线路扫描，并按 revision 缓存小型结果；状态写入口会失效缓存。
- 独立公开哈希函数继续作为测试 oracle，融合结果必须逐字节一致。

### 2.3 相同 revision 重复保存

- Simulation Worker 只在 runtime revision、实体/线路数量、连续 chunk 范围、上一份 manifest 元数据和物理 chunk 身份全部相符时复用集合页。
- 复用时只生成并提交新的 base/manifest，不再投影、序列化、哈希或通过 IPC 发送全部实体/线路页。
- 新模拟 revision、记录数量变化、证明缺失、Worker 替换或写入失败都会清空缓存并回到完整确定性分块路径。
- 这是“同一权威 revision 的重复检查点”优化，不把活动模拟中的不同 revision 伪装成未变化。

### 2.4 Windows 包跨平台残留门禁

- Electron files 规则显式排除 Capacitor 依赖目录中的 `android/build/**`。
- 每次 `desktop:pack` 和 `desktop:dist` 生成后同时检查 `app.asar` 与 `app.asar.unpacked`；发现 Android Gradle 产物即失败。
- 本轮先实际执行 Android Gradle 332 个任务，再构建 Windows 包，验证最坏构建顺序下仍无残留。

## 3. 76.9 MB 真实存档只读实测

测试附件为 `76,898,141` 字节、`80,674` 个实体、`155,746` 条线路。原文件只读使用；文件 SHA-256 在测试前后均为 `ab869c2b52d5f89e1fcbd8bfcb715daa2f5e7b02b4b7d1bd553f12f566531554`。

### 3.1 原生核心

| 指标 | 1.2.0 基线 | 1.2.1 本次 | 观察结果 |
| --- | ---: | ---: | ---: |
| 原生载入与索引 | 12,870.90 ms | 8,285.01 ms | 下降 35.63% |
| 原生进程 Private Bytes 增量 | 342,900,736 B | 295,608,320 B | 减少 47,292,416 B / 13.79% |
| 顶层暂停命令 | 未单列 | 60.13 ms | 未重建整厂索引 |
| 一秒原生精确推进 | 1,989.22 ms | 2,065.12 ms | 单次运行有噪声，未宣传为推进本身提速 |
| 同次 JavaScript 一秒推进 | 3,018.72 ms | 3,275.99 ms | 环境随本次同机对照变化 |
| 本次原生相对 JS 吞吐 | 约 1.52 倍 | 约 1.59 倍 | 状态精确一致 |
| 首次完整诊断 | 12,904.50 ms | 2,353.27 ms | 下降 81.76% |
| 同 revision 重复诊断 | 未缓存 | 0.17 ms | 复用已验证摘要 |

原生与 JavaScript 推进后的规范字段、根哈希和组件哈希完全一致，字段差异为 0。单次时延会受系统负载影响；这里只把同机、同附件、同候选的原始数字作为开发证据，不承诺所有玩家得到固定比例。

### 3.2 重复分块保存

| 场景 | 处理时延 | 写记录数 |
| --- | ---: | ---: |
| 首次完整集合种子 | 1,758 ms | 158 |
| 同一 Worker revision 再次保存 | 3 ms | 1 |

本次测试记录的集合投影/传输处理量下降约 99.8%。该数字不代表活动模拟每次自动保存都只有 3 ms；只要 revision 改变就会恢复完整确定性分块路径。

### 3.3 JavaScript 权威线路观察

三次真实权威推进分别为 `2,140 / 2,056 / 1,822 ms`，对应投影为 `25 / 27 / 26 ms`。每步仍检查 `311,492` 条线路方向，78,025 个路由组中 77,445 个为活动组；该档确实持续有大量 source-empty 或 target-full 状态，当前不能在没有唤醒证明的情况下把它们全部跳过。1.2.1 没有用降低结算频率、减少产量或错误休眠线路换取性能数字。

保守纯挂机真实档守恒专项通过：不确定尾段保持冻结、结果可重载、源附件哈希不变。

## 6. 下一步边界

1. 1.2.1 只交付已经验证的热路径优化，继续保持原生权威关闭。
2. 后续若继续完成第二层，优先补 10,000 次随机故障、覆盖升级和杀软锁文件，而不是继续增加新格式功能。
3. 后续若继续完成第三层，必须先完成 CORE-370，再以 24 小时、多硬件和 IPC/总内存证据决定是否批准 CORE-390。
4. 正式签名、部署、下载页、生产备份和灰度由独立 Release Agent 在固定 clean SHA 上执行；本开发候选不越权。
