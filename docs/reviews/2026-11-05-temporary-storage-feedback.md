## 已复现的边界

本地 IndexedDB 无法打开且 localStorage 无法取得时，兼容层以 `memory` 后端、`primary` 写角色继续临时运行。旧提示组件把 primary 一律视为正常；旧保存会先遇到证明路径失败，再经内存缓存读回而显示“存档已验证完成”。这说明缓存与持久保存反馈混淆，不等于磁盘原档被覆盖。

`temporary-storage-red-30` 完整复现（1 用例、3 个反馈断言失败）：原档/恢复后分别铁矿 **42→42**、电磁学完成、原始蓝图、自动保存间隔 **0→0**；临时进度为铁矿 100，9,076 B 导出文件确实含临时 100，页面异常 0。缺少临时提示、把缓存显示为保存完成、缺少未保存反馈，分别保留失败。所有数据均为本机隔离浏览器合成。

较早 `red-28` 未识别实际进度反馈文字，`red-29` 使用了迁移会过滤的无效科技 ID；这两轮属于测试准备问题，不作正式产品反例。已改用有效电磁学并在故障前读取规范化原档，恢复后严格比较完整摘要；没有放宽保档断言。

## 实现边界

- 网页 primary+memory 有常驻临时运行提示；只读、冲突、连接变化和原生平台继续原有反馈。
- App 私有保存入口在普通 memory 保存开始前返回 unavailable，反馈不能写入本机；不再申请无意义的保存检查点或把缓存确认当作保存成功。
- 导出是显式独立用途：沿用同一精确检查点、权威租约和内存屏障，通过现有 Worker 序列化生成文件正文，跳过主档、备份、journal 和证明提交。只把正文交给当前下载流程，不回写磁盘。健康存储继续原保存/读回流程，Rust 权威保护先于这些分支。
- 活跃的实验恢复会话无法走独立内存导出时明确失败，不降级为旧 JS 状态。公开 SaveGameResult、存档格式、写入围栏、原生 IPC 与备份设置不变。
