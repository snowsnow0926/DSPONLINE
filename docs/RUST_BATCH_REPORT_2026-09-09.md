# Rust 开发批次报告｜2026 年 9 月 9 日

这批已经完成并提交。最重要的进展是：**Rust 的计算收益已经有了实测，Windows 开发包也首次完成了本轮公开工厂的“真正采用 Rust 结果 → 保存 → 正常退出 → 重新进入”验证。** 取消计算后，原存档和原生检查点也都保住了。

但这还不是“全游戏 Rust 版已经做好”。当前通过的是有明确条件的小工厂、短离线流程；终局大工厂的完整等待收益、长时间离线以及实时模拟接管仍未完成。本批没有发布或替换玩家正在使用的版本。

## 1. 用小白能懂的话说，现在做到哪里了

可以把 Rust 当作新的计算引擎。我们已经证明它在部分任务上更快，也修复了把结果送回游戏时遇到的几处问题。这批的重点是让“算得快”开始接上“玩家确实能保存并继续玩”。

| 工作 | 当前状态 | 对玩家意味着什么 |
| --- | --- | --- |
| 大存档的保存、导入和离线准备优化 | 共享部分已随 1.2.7 网页/安卓发布 | 已有收益，不要求客户端运行 Rust |
| Rust 核心计算提速 | 多个局部场景已有对照实测 | 新引擎值得继续投入，但不能据此推算整个游戏快几倍 |
| Windows 短离线完整流程 | 本批公开样本通过 | Rust 结果能经真实界面采用、保存，并正常重开 |
| 终局档完整离线流程 | 尚未完成 | 还不能承诺终局玩家从点击到能玩的等待缩短多少 |
| 数分钟、数小时离线自动采用 Rust | 继续关闭 | 仍需证明复杂工厂的产出正确，不能直接放开 |
| 游戏运行中全面由 Rust 计算 | 未开放 | 普通实时模拟仍由现有 JS 流程负责 |
| 网页、安卓直接运行 Rust 核心 | 后续阶段 | 本批原生接入修复主要用于 Windows 开发包 |

我们处于 **RP1：把原生离线收益接入实际游戏并验证** 的阶段。RP1 的公开短流程已有进展，整个 RP1 还没有验收完成。不用一个模糊的“完成百分比”把后面这些大工程掩盖掉。

## 2. 已测到的提速有多少

以下是本轮持续开发以来各阶段的独立实测，比较对象和范围不同，不能相加。

| 测试内容 | 测量结果 | 应当怎样理解 |
| --- | --- | --- |
| 公开小工厂精确计算 1 小时游戏时间 | 旧 Rust 约 32.50 秒 → 新 Rust 约 3.19 秒，耗时下降 90.2% | 三对独立进程对照；只测这个计算请求，不含加载、界面和保存 |
| 授权终局档的 Rust 开档步骤 | 约 14.03 秒 → 9.28 秒，下降 33.9% | 对比此前 Rust 实现；不是整个游戏启动时间 |
| 上述终局开档的 Host 内存峰值 | 约 2.34 GB → 1.37 GB，下降 41.3% | 指这个原生进程的私有提交内存，不是整机或整个客户端的内存 |
| 终局档精确推进 5 个游戏秒 | Rust 请求约 10.69 秒；JS 计算约 30.31 秒 | 单次诊断，结果完整相同；还不是正式的多轮完整等待对照 |
| 本批公开工厂点击继续到能操作 | 约 1.66 秒 | 仅 110 个实体、2 条传送带、5 秒离线；是流程观察，没有新旧配对，不能作为提速百分比 |

所以现在可以说“Rust 的几个关键步骤确实更快”，还不能说“终局玩家整个游戏已经快了 90%”。以前共享导入等优化的比例也主要来自 Windows 实测，网页和安卓虽然用了相同共享代码，不能保证设备上出现相同百分比。

## 3. 这批具体修了什么

1. **恢复后的好存档被误判不能继续。** 原来目录记的是原主档，恢复后正文顺序或内容合法变化，却被拿去跟原目录直接比较。现在分开核对原主档身份和恢复结果。
2. **恢复后保存误报另一个窗口改了档。** 保存比较基准现在保留真正的磁盘原文，合法恢复不会混进这个基准；真正的跨窗口冲突保护仍然有效。
3. **旧恢复记录可能把新存档时间倒回去。** 相同游戏状态不代表同一保存时间，现在先检查时间先后，再读取恢复块。
4. **桌面入口引用了不存在的旧变量名。** 这使 Rust 尚未开始计算就回退到 JS。现在普通版和性能开发版各用正确的固定存档目录。
5. **正确的短时 Rust 结果被通信校验器拒绝。** 校验器现在认识“最多 30 秒、全部精确计算、没有估算尾段”的结果；超范围的正常拒绝也能正常传回。

后两项来自实际打包客户端运行，不是只看代码推测。它们解释了为什么“内核单测通过、计算也正确”，玩家入口仍可能吃不到收益。

## 4. 怎样确认没有把玩家进度弄坏

在本地隔离的 Windows 包上，使用公开生成的工厂和预先准备的匹配运行检查点，两个流程通过：

- **完成流程：** 点击继续 → Rust 实际计算 5 秒 → 与 JS 完整结果核对 → 游戏实际写档 → 界面暂停并手动保存 → 正常退出 → 重开时磁盘状态相同 → 再进入工厂时完整状态与正常 JS 加载相同 → 再次退出重开一致。
- **取消流程：** 等真正的 Rust 候选算好后点击取消 → 原主档逐字节不变 → 原生检查点的代数、修订和根摘要不变 → 正常退出并连续重开，原档仍不变。

取消测试为了稳定点到按钮，在 Host 已经算好后把响应延迟了 3 秒；它用于验证取消保护，不用于性能计时。最终两个流程共记录 **8 次正常进程退出，退出码均为 0**，没有强制结束成功样本。

重进工厂时，普通加载器会移除一个未安装喷涂器上的零值进度项。我们保留了这个差异，分别核对原始磁盘状态和正常 JS 加载后的完整状态，没有忽略某些字段来制造相同结果。

本批最后的客户端流程验证使用公开夹具，没有上传真实玩家档。此前终局档测量使用的是授权文件副本，原文件不变。

## 5. 测试有没有全部通过

与本批最终桌面修复直接相关的完整 Native 工具测试是 **632 通过、1 条件跳过、0 失败**；生产构建、包内身份和 75 件制品的摘要检查通过。最终公开结算与取消两条实际包流程均通过。

共享恢复修复另有 35 项专项通过、22 项实际浏览器恢复/保存协调检查通过。广泛回归的原始结果必须保留：全量单元曾有 3 项失败，其所在文件独立复验 137 项通过；全量浏览器曾有 105 项失败，随后分批复验全部通过。**这不等于重新跑过一次完整全绿的发行矩阵。** 最后独立菜单响应检查为 277 毫秒，低于原 500 毫秒门槛，门槛没有放宽。

测试期间修正了公开夹具和驱动中的运行状态、自动保存偏好、保存修订/目录元数据及弹窗处理问题，失败记录全部保留。没有修订记录的旧式测试档曾被正常关闭保护拒绝；旧档自动补齐元数据的退出兼容性仍需单独验证，不能从最终标准夹具通过推算所有旧档都没问题。

## 6. 哪些客户端现在能用

按 9 月 8 日已验证的发布记录，网页和安卓 1.2.7 已包含共享优化；Windows 公共下载仍保留 1.2.6。**这批新的 Rust 接入修复只在本地 Windows 性能开发包，尚未发布。** 本批未重新查询或操作线上服务。

开发包沿用内部版本号 1.2.7 便于与现有开发线衔接，这不表示又发布了一次 1.2.7。后续公开版本号应在发布范围确定后再定。

## 7. 下一批优先做什么

优先补 **真实终局档的完整用户等待对照**：把加载、证明、Rust 计算、校验、写档和进入界面一起计时，与现有 JS 路径做独立配对，确认最终状态和取消保护。它最能回答“玩家到底少等多少”。

接着验证正常游戏写出来的检查点，以及旧档元数据恢复和退出兼容性；本批是预先准备的匹配运行检查点，不能覆盖所有自然保存来源。

再根据实测决定怎样扩展较长离线时间、复杂工厂和证明预算。历史一次堆异常的根因、多设备稳定性、完整发行检查以及 Windows 签名仍是独立缺口。超过 30 秒自动采用、实时接管和跨端 Rust 接入都保持后续范围。
