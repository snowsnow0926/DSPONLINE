# 现有 Rust 规划器的网页复用验证

Role: develop。结论：**可以在浏览器里运行，但现有接口直接接入会更慢，当前不接入游戏**。基础计算和完整递归规划要分开看；不能用编译成功或单独 Rust 函数的速度代表网页收益。

## 实现与范围

新增 `experiments/web-construction-wasm` 独立探针，直接编译当前 Rust 规划器源文件；只提供它需要的目录外壳，不改原生 Host，不维护另一份算法副本。JS 保有游戏状态；实验只传递目录、目标、相关库存和科技。无 npm 新依赖，Rust 依赖由独立 lockfile 固定，生成文件留在忽略目录。

Chrome `147.0.7727.138` 中验证 **285/285**：283 个真实目录/库存/科技组合，2 个多路线与共用原料回退组合。比较可制造性、配方顺序、批次数、输出数量和重放后的每项库存；126 个明确原料短缺结果也一致。没有验证 UI 原因文案、建造调度、量子预算、退款、电力或整个存档，因此没有完整替代现有后端的资格。

## 实测

每组完成预热后交替先后顺序，计时五次取中位。各组调用数量不同，横向比较同一行，不能比较不同行的总毫秒。

下表由 [探针证据](./evidence/2026-10-26-web-wasm-probe.json) 记录；端到端包括 JSON 编码/解析、内存复制、调用及材料核对。另测排除这些费用、预载所有请求的纯计算下限，仅用于区分算法与接口成本。

| 场景 | 每次样本调用数 | JS 端到端 | Rust 端到端 | JS 纯计算 | Rust 纯计算 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 现成库存 | 5,488 | 36.7 ms | 82.8 ms | 30.3 ms | 6.6 ms |
| 真实配方递归 | 672 | 12.6 ms | 97.0 ms | 11.9 ms | 80.3 ms |
| 缺料 | 4,272 | 42.6 ms | 82.0 ms | 40.6 ms | 14.2 ms |
| 多候选/共用原料 | 4,800 | 18.1 ms | 176.2 ms | 15.5 ms | 117.9 ms |

当前结果中，库存够用和缺料场景的 Rust 纯计算较快，但端到端均慢于 JS；需要递归的场景，Rust 纯计算本身也较慢。检查代码可以解释这一差异：原生规划器仍提前展开最多 24 个候选，网页 JS 已能在找到第一个完整可行方案后结束；因此必须先优化原生规划策略，再测量紧凑接口。

WASM 文件约 0.75 MB，实验中线性内存约 2.95 MB；这些仅是规划探针数据，不能作为整款游戏内存结论。目录初始化也单独记录，不计入每批纯计算。

## 验证及下一步

- `cargo build --release --target wasm32-unknown-unknown --locked`、`cargo fmt --check`、实验 TypeScript 检查和浏览器差分通过。
- 游戏 `src`、原生 `native`、项目依赖及已冻结 Web 包未改，上一轮完整回归仍对应同一运行源码。
- 不接入变慢的 JSON 路径。保留 Rust 复用方向，先试按需规划、固定目录编号和紧凑数组，再计入真实调用、校验和回写成本。
- 大档 Chrome 对照同时发现整档打包仍约 2.7 秒。下一轮先查读取、保存和 Worker 交接中的重复复制，避免只优化数学运算而遗漏实际等待。

上述结果只属于开发实验；没有发布到香港网页或桌面/安卓端，没有修改真实存档或自动备份设置。
