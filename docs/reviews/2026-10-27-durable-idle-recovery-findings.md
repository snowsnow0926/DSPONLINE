# 可选恢复模式：纯挂机停止与取消的既有失败

状态：待定位修复；对照已确认并非本轮退出性能改动新引入。
该恢复模式由 `VITE_DURABLE_RUNTIME_RECOVERY=true` 显式启用，默认网页构建没有启用。
所有测试使用独立浏览器和合成存档，没有访问生产服务器或玩家存档。

## 已观察到的情况

在已撤回的第一版候选上额外启用该模式，运行纯挂机恢复扩展用例：8 通过、2 条件跳过、3 失败。
对同样的 3 个失败用例，使用上一轮干净源码 `c01ad5dcc2fb` 重新运行，3 项以相同断言和现象失败。
最终保留方案又单独重跑这 3 项，失败用例和错误特征与上一版完全相同。第一版候选、最终保留方案
与基线版的失败截图、跟踪、日志和 JSON 报告已分别保存在本机忽略目录
`D:/GameDev/DSPidle2/artifacts/web-stop-transfer-20261027/`。

1. 主档已提交但恢复日志提交失败后，点击放弃旧检查点，界面在 5 秒内仍显示原保存错误，
   没有显示要求重试、禁止回退的提示。测试在提示断言处停止；是否发生主档回退需继续独立核验。
2. 写入失败后明确放弃候选，重新点击开始产率复制，5 秒内未出现新的纯挂机窗口；原因待查。
3. 终态候选已生成、验证日志被测试门栓阻塞时点击取消，恢复记录的原因在 5 秒内仍为
   `user-stop-requested`，没有变为 `user-cancelled`。测试在放开门栓之前停止，
   尚不能据此断言随后是否发生写入；须验证用户取消的实际边界和主档最终状态。

最终保留方案的官方专项 `npm run test:e2e:durable` 为 7/7 通过；这不覆盖上述 3 项扩展场景，
也不抵消这些失败。第一版候选的默认网页完整回归为 488/33；撤回后的保留方案重新运行后为
486 通过 / 33 条件跳过 / 0 失败，不能把两次结果相加。

## 后续验证方向

- 分别记录取消点击前后、释放验证门栓前后、页面刷新后的主档身份及恢复记录。
- 主档已提交时不得回退；提示应让玩家看见。尚未提交且仍可安全取消时，取消应阻止之后的写入。
- 明确写入已经开始时的不可取消边界，避免界面把等待确认误呈现为已取消。
- 排查放弃后重新开始的所有权、恢复日志和模拟 Worker 接管；保留材料、存档及备份设置。
- 以旧版与修复版的同一故障注入、复读和刷新结果验收；不得靠放宽断言或直接删除恢复数据通过。
