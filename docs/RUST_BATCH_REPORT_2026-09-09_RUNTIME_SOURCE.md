# Rust 开发第二批报告｜2026 年 9 月 9 日

**这一批补好了一个关键底层能力：普通存档可以交给 Rust 临时计算，无需先覆盖另一套原生存档。测试通过并随本报告提交，但“继续游戏”按钮还没有接上这个新能力。** 本批没有发布新版本，也没有新的“玩家等待缩短多少”的实测结论。

## 1. 为什么需要做这一步

上一批用预先准备好的存档证明了：Rust 能算对，结果能经过 Windows 界面保存并重新打开。继续测试普通玩家的保存流程时发现，游戏正常保存后，并不会同步生成当时这条 Rust 路径需要的原生检查点。于是它可能找不到相符的来源，又回到现有 JavaScript 计算。

可以把这次工作理解为补齐新计算引擎的存档入口。引擎有了局部提速，接下来要让正常游玩的存档也能送进去。

## 2. 本批完成了什么

- **临时计算：** 从已经加载并验证的完整游戏状态建立一次性 Rust 状态，算完返回待验收的结果。
- **保护旧档：** 计算期间不覆盖原生主档，不写进度日志，也不留下新的长期会话。放弃结果后，旧档仍在。
- **来源核对：** 文件内容、大小、保存时间或完整状态证明不对，就拒绝计算或返回结果。
- **控制范围：** 仍只准许 1–30 秒的精确离线候选；没有把长挂机、实时模拟一并放开。

这样不需要让每次自动保存都再额外写一份完整的原生档，避免先引入新的大档保存负担。真正的传输开销仍需要下一步实测。

## 3. 测试证明了什么

| 验证 | 结果 | 可以得出的结论 |
| --- | --- | --- |
| 完整 Rust Host 测试 | 252 通过，0 失败 | 新接口通过保存、恢复及旧协议相关回归 |
| 新的真实进程专项 | 22 通过，0 失败 | 接口在真实 Host 上可用，不只是在内部函数里可用 |
| 三类公开工厂，各算 1、5、30 秒 | 9 组完整状态与 JS 相同 | 本次范围内产出和完整游戏状态一致 |
| 空原生档、旧原生档、丢弃结果和正常重启 | 通过 | 这些场景没有改坏来源或悄悄提交进度 |
| 完整 Native/桌面工具检查 | 654 通过，1 条件跳过，0 失败 | 当前 Host 与既有桌面工具的回归检查通过 |
| Rust 严格静态检查及编译 | 通过 | 当前实现可以编译，没有该检查发现的警告 |

三类工厂分别是普通产线、有限矿储量、量子仓储接近容量上限。验证比较所有状态字段，不只是最后的物品总量。

测试过程中也有失败：新增测试曾读到 Windows 独占空锁、混用了两种信封校验方式，以及没有等旧进程退出就重启。这些测试问题已修正，原失败日志保留。本批没有修改产品的存档校验规则来绕过失败。

## 4. 玩家现在能获得什么

**这一批属于开发中的接入工作，尚未直接交付给玩家。** 之前记录的 Rust 开档、精确计算提速仍有效，但各自只适用于当时测量的步骤；不能把它们相加，也不能说整个游戏已经快了相同比例。

| 客户端 | 本批状态 |
| --- | --- |
| Windows | 新 Host 能力已实现并验证；新传输与实际入口待接，未发布 |
| 网页版 | 继续使用已发布的共享优化，本批没有接入 Rust |
| 安卓版 | 同上；Rust 跨端接入仍在后续计划 |

本批仅使用本地公开合成工厂，没有修改或上传玩家存档，没有连接生产服务器。

## 5. 接下来按什么顺序做

1. 把临时来源的分块传输接到 Windows 主进程和继续游戏按钮，控制大档内存与超时。
2. 用自然保存后的真实界面走完计算、取消、保存和正常重开，确认普通玩家的流程确实能采用 Rust 结果。
3. 用授权终局档比较从点击到可以操作的完整等待，做多轮独立对照，给出可复核的实际收益。
4. 在正确性和成本证据足够后，再逐步扩展数分钟、数小时离线范围；实时和网页/安卓接入仍是后续工程。

当前仍在 RP1“把原生离线计算接进游戏并验收”的阶段。底层又补齐了一环，但 RP1 总验收尚未完成。下一批最值得做的是把这条入口真正接通，之后才能判断终局玩家到底能少等多久。
